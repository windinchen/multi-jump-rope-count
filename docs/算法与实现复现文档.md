## 1. 任务定义与硬约束

**输入**：一段固定机位（或手持但有明显人体尺度）的视频，画面中 1~16 人在跳绳，人可能互相遮挡、离开画面、被检测框短暂跟丢；画面里同时存在不走跳绳动作的路人。

**输出**：每个人在本段的起跳次数（逐人分列 + 总量），以及"这个数字为什么可能不准"的可解释说明。

**硬约束（按优先级）**：

1. **不重训模型**。使用给定的 `跳绳素材/yolo26s-pose.pt`（Ultralytics YOLO26s-pose，COCO 17 关键点）。任何"换一个更好的姿态模型/重训一个计数头"的方案都不作为前提。
2. **该数的必须数到**：一次真实起跳被漏掉的代价高于一次轻微不确定。
3. **不该数的不能数**：站着抖腿、走动迈步、机身抖动、检测框抖动，都不能产生计数。
4. 第 2、3 条冲突时的裁决原则：**先保证不双计（一次跳不能数两遍），再从"按节奏本该有跳"的空档里回捞**。理由：双计是乘法级污染（节奏一歪整段虚高），漏计只是加法级损失。

**计数口径定义**（全流程唯一，改任何一层都不能改这里）：

- `count`（起跳数）：一次离地 = 一个计数。双摇（一次起跳绳过两圈）仍算 **1** 次。
- `count_rope` / `rope`（过绳数）：把双摇的第二圈也算上，= 起跳数 + bump 数 +（离线）按节奏补齐数。
- 对外总量 = `count + filled`（实测起跳 + 按节奏补齐），其中 `recovered`（包络回捞）是 `count` 的子集，单独列出不重复相加。
- `policy` 配置项控制对外报 `jump` 还是 `rope`，默认 `jump`。

## 2. 系统总览

两条链路共用同一套阈值与判据函数（`counter.py` / `signal.py`），差别只在"信号是整段重算还是滑动窗口重算"。

```
mp4 / 摄像头
   └─ detect.py      YOLO 检测+姿态 → Detection(box, keypoints, conf)
        └─ detect.suppress_duplicates   同一人重复框抑制（防一次跳数两遍）
             └─ tracking.Tracker        IoU+中心距离贪心关联、速度预测、断轨重认领 → (track_id, det)
                  ├─【离线】pipeline.run  按 track 累积样本
                  │     └─ identity.py   站位身份 + 碎帧缝合 + 重复轨迹合并
                  │           └─ counter.count_track   信号→阈值→节奏→峰→回捞→补齐→三态判定
                  │                 └─ audit.audit      逐条解释"为什么可能数错"
                  └─【实时】online.OnlineCounter  每人一个滑动窗口计数器
                        └─ engine.Engine  读帧/推理/出图循环，MJPEG + JSON 快照
                              └─ web/app.js  卡片、事件流、灵敏度滑杆
```

关键设计决定：

- **计数的最小单位是"一条身份归并后的轨迹"**，不是"一帧一个框"。所有误差治理都发生在轨迹级。
- **所有阈值都是"相对于这个人自己的信号"**（噪声、峰值 p95、自己的节奏周期、自己的框高），不用跨人绝对阈值。远景人近景人共用一套代码。
- **每一次"多出来的数"都带来源标记**：`kind="interpolated"`（按节奏补）、`recovered=True`（包络回捞），页面上分列显示，便于复盘时单独关。

## 4. 数据契约

定义在 `jumpcount/types.py`。跨层传递只有这几个结构，改协议先看这里。

| 结构 | 用途 | 关键字段 |
| --- | --- | --- |
| `Detection` | 单帧单目标 | `frame`, `time`, `box=(x1,y1,x2,y2)`, `conf`, `keypoints[N,3]`（COCO 17 点，第三列置信度已 clip 到 0~1） |
| `sample` 元组 | 一条轨迹的逐帧观测（离线链路的主输入） | `(frame, time, box, feature_y, keypoints)`；`feature_y` 允许为 `None`，由选源逻辑补齐 |
| `JumpEvent` | 一次计数事件 | `frame`(浮点，亚帧), `time`, `amplitude`, `confidence`, `kind ∈ {jump, bump, interpolated}`, `recovered: bool` |
| `TrackResult` | 一条轨迹的最终结果 | `count`, `count_rope`, `period_sec`, `rate_hz`, `signal_source`, `visibility`, `median_height`, `snr`, `stats`（审计与判定的全部依据） |

`stats` 是被审计、判定、页面三方共用的字典，新增字段必须同时想清楚三处消费方。常用键：
`verdict`/`participant`/`excluded`/`provisional_reason`、`count`/`filled`/`recovered`/`total_count`/`expected_count`/`rhythm_coverage`、`noise`/`amplitude_threshold`/`peak_level_p95`、`rhythm_strength`/`period_source`、`excursion_ratio`/`ankle_sync`/`lift_ratio`/`lift_ratio_best`/`height_cv`/`visibility`、`estimated_misses`/`misses_unobserved`/`long_holes`、`channel_scores`。

坐标系约定：图像坐标 y 向下为正；进入信号处理前统一取负（`raw = -y`），**向上为正**，所以"起跳"是正向峰。全流程都按正向峰讨论。

## 5. 误差来源分类（决定了后面每一层为什么存在）

| 误差 | 现象 | 对应处理层 |
| --- | --- | --- |
| ID 漂移（分裂） | 一个人被拆成 3 条轨迹，每段各丢一段 warmup 与断档跳跃 → 总量偏低 | 6.3 断轨重认领、6.4 碎帧缝合 |
| ID 漂移（合并） | 两个人并成一条轨迹 → 偏高，且 `height_cv` 爆表 | 6.2 重复框抑制、6.4 重复轨迹合并、6.14 框高波动闸门 |
| 遮挡/跟丢 | 空档期没有观测，跳了数不到 → 偏低 | 6.13 按节奏补齐、6.15 可见率口径 |
| 远景小幅起跳 | 170px 身高的人真实离地在踝部只留 1~2px，被绝对像素下限砍掉 → 偏低 | 6.9 像素下限按框高缩放、6.12 能量包络回捞 |
| 机身/透视抖动 | 整段信号平移，噪声估计虚高或虚低 → 双向 | 6.7 去基线、6.8 只用真观测段估噪声 |
| 走路路人 | 迈步被数成起跳 → 偏高 | 6.14 横向位移 + 双脚相关性 + 三态判定 |
| 一次跳数两遍 | 峰被检出两次（升沿/降沿、框抖动）→ 偏高且节奏歪 | 6.11 不应期、6.12 能量积分把两沿并成鼓包、6.12 回捞的两道节拍闸 |
| **快跳 2:1 锁相** | 跳得越快反而数得越少：估出的节奏要么恰好是真实值的一半，要么被判「测不出来」退回 2.0Hz 区间中点 → 偏低且腰斩 | 6.10.1 `max_rate_hz=4.5` + 四处最短间隔一律向下取整 |
| 前景行人带动框底边 | 框里的人没动，前一个人经过把框底边抬走，造成假的规律波纹 → 偏高 | 尚未处理，见第 12 节第 4 条 |

## 6. 逐层算法

### 6.1 检测层（`jumpcount/detect.py`）

YOLO 一次性出框和 17 关键点（`UltralyticsDetector`）。默认 `imgsz=1280`：2560×1440 监控画面用 640 会把人压到 ~80px，关键点闪烁严重，比计数算法本身的误差还大。`conf=0.35`，`classes=(0,)`（COCO person）。

关键点第三列一律 `clip(0,1)` 后存储（不同版本 Ultralytics 的语义不一致，有的输出的是未 sigmoid 的 logit）。

另有一个不依赖 torch 的像素回退检测器（`PixelDetector`），用于在没有 GPU/权重时验证跟踪+计数链路。

### 6.2 重复框抑制（`detect.suppress_duplicates`）

同一帧同一个人出两个框 = 同一次起跳被数两遍。判重两条路：

- `IoU >= nms_iou`（0.45）→ 判重；
- 或同时满足：中心水平距离 `<= dup_center_ratio × min(h)`（0.3）、框高差 `< 0.35 × max(h)`、`IoU >= dup_min_iou`（0.25）→ 判重。

第二条的 `IoU >= dup_min_iou` 是补丁：紧挨着站定的两个人中心距离可以只有半个身位，只按距离判重会把旁边那位的框整帧吃掉，他后面所有起跳再也没有观测。

保留规则：按 `conf` 降序贪心保留。

### 6.3 跨帧跟踪（`jumpcount/tracking.py`）

手写贪心关联（不引 ByteTrack，避免第二套身份体系与站位冲突）：

- 得分 `score = match_iou_w × IoU + (1 - match_iou_w) × 中心距离得分`，中心距离得分按 `exp(-d / (match_scale × h))` 衰减，`d` 是速度外推后的中心距离（每帧维护 `vel` 做恒速预测，用于遮挡期）。
- `score < match_thresh`（0.35）不关联，走新建轨迹；新建需连续命中 `min_hits=3` 帧才对外可见（抑制单帧闪烁误检出计数）。
- 丢失 `max_age=25` 帧才丢弃轨迹。这个值是从 15 放宽到 25 的：16 人群像里人被人挡 1 秒是常态，15 帧时有 470 次"已经数到却被整段丢弃"，放宽到 25 后降到 289。
- 断轨后保留 `reid_window=45` 帧的重认领窗口，允许中心距离 `reid_dist=0.9 × h`，让被遮挡的人接回原 ID。

三条硬约束（`tests/test_core.py::TestTrackingGuards` 锁住）：

- **一条轨迹一帧只配一个框**。断轨重认领（步骤 1）会把认领回来的轨迹塞进 `active`，紧接着的常规贪心关联（步骤 2）原本还能让它再抢一个框：同一个人同一帧配到两个框，框位与框高被写两次、`hits` 翻倍，画面上的数字也会跳。现在步骤 2 跳过步骤 1 已经配对过的轨迹，抢不到框的那位按新建轨迹处理。
- **长跑必须封顶**。`_Track.heights`（算框高中位数用）、`Tracker.all`、`Tracker.events` 都改成定长 `deque`（`HEIGHT_HISTORY=600` / `TRACK_HISTORY=4000` / `EVENT_HISTORY=5000`）。摄像头连开几小时时不封顶会让单条轨迹的框高列表涨到几十万，每帧的 `np.median` 从微秒级变成毫秒级，内存也跟着吃光。600 帧 = 25fps 下 24s，比在线信号窗口还长，中位数取"最近这段"反而更贴合当前距离；6 段素材整段复算结果与不封顶时完全一致。
- **认领回来的轨迹必须离开断轨池**。`_revive()` 过去只把轨迹加进 `active`，没有从 `finished` 里摘掉，于是它**第二次**断开时会被再塞一次进池子：同一个对象在池里留下两个引用。下一帧只要有两个框都能匹配上（人挨着站、或检测器给出重复框），`used_f` 是按**下标**去重而不是按对象去重，两条引用能把同一条轨迹认领两遍——`active` 里出现两个自己，`tracker.update()` 同一帧返回两个相同轨迹号。更麻烦的是认领判据是中心距离（`reid_dist × h`）而不是 IoU，第二条引用会顺手把**隔壁那个人**这一帧的框吃掉，那人当场没有轨迹，整段容易被并进旁边的人。修法：认领成功后按下标倒序 `self.finished.pop(fi)`（与同一函数里吃掉 `pending` 的写法一致）。

  实测影响（唯一变量就是这两行，留痕 `out/tune/DOC_fix_reid_off.log` / `DOC_fix_reid.log`）：离线合计 3845 → 4101，实时链路 3912 → 4446，判为在跳绳 65 → 73；同时双计特征 5.75% → 4.28%、回捞峰自身双计 0.34% → 0.00%、被剔除但已数到的次数 296 → 128、虚高仍是 0 条。两条"数重了"的直接证据同时下降，说明多出来的次数不是把一个人拆成两个人数出来的；按位置逐条比对，`1790234843854` 里多出的计入人员中有一位（横向 1773px、手里有绳、被观测 36.9s）在修复前的整段结果里连对应的框都没有。完整率 0.721 → 0.687 是分母变了（"应有次数"由每条被计入轨迹自己的时长 × 节奏推出，多 8 个人分母涨 12%），属于自我一致口径，不能当退步证据。

### 6.4 身份归并（`jumpcount/identity.py`）

跟踪输出的轨迹仍会分裂/重复，计数前先归并成"人"。

**站位（slot）身份** `slot_identity=True`：为每个人维持一个"站位"，轨迹失联后计数由站位保管，新轨迹回到站位附近时接管数字。参数：

- `slot_dist_ratio=0.5` 认领允许的最大水平距离 / 框高；
- `slot_claim_gap=8` 站位空置 8 帧后才允许新轨迹认领（防止把旁边的人并进来）；
- `slot_height_ratio=1.6` 认领允许的框高变化倍数；
- `slot_overlap_iou=0.55` 框重叠超过此值直接认领（即使站位刚被占用）——同一人另立新框是常态，宁可先认再校验；
- `slot_keep_frames=250`（约 10s）后彻底忘记站位；
- `ghost_display_sec=0.35` 失联超过这个时间就不再画框/脚标（**计数仍由站位保管**，只是画面不定格）。

**碎帧缝合**：时间间隔 `<= merge_gap_frames`（60 帧）且水平距离 `<= merge_dist_ratio × h`（0.9）的两条轨迹并成一条。

**重复轨迹合并**：时间重叠比例 `>= dup_overlap`（0.5）且水平距离 `<= dup_dist_ratio × h`（0.45）且重叠帧上框 IoU `>= dup_iou_min`（0.35）→ 判定是同一个人的两条轨迹，合并（否则同一次跳被算两遍）。

`dup_box_iou=0.5` 只影响画面：两个框重叠超过此值时把更旧的那个从画面上去掉，**不影响计数列表**（砍掉的框会连带砍掉他的计数，见 `engine._hide_duplicate_boxes`）。

### 6.5 信号提取（`counter.feature_y` / `channel_y` / `extract_y_detail`）

候选信号源：`ankle`（15,16）、`hip`（11,12）、`head`（0）、`box_center`、`box_bottom`（`config.COCO_KEYPOINTS` / `AUTO_ORDER`）。

- 可见性过滤：关键点 `conf >= kp_conf`（0.30）且坐标非负。
- **双踝合成 `ankle_combine="high"`**：取两只脚踝中**抬得更高**的一只（y 更小）。这不是可有可无的优化——左右脚交替抬的跳法里，取均值会把一半起跳压到阈值以下，实测同一个人脚踝取均值只数到 29、取较高一只数到 45，且已计峰间隔正好是节奏周期的两倍（典型的"漏一半"特征）。
- `channel_cache` 把 5 个通道一次性算完缓存，后续选源/回捞/幅度对照都复用（这是离线链路最大的常数优化）。
- **替身链补齐** `SUBSTITUTE_CHAIN`：主通道某帧取不到点时，按链找替身通道（如 ankle→hip→head→box_bottom），并用"两者同时可见帧上的中位差"把替身平移回主通道尺度：

  ```
  shift = median(primary[both] - alternate[both])
  values[missing & isfinite(alternate)] = alternate[missing] + shift
  ```

  为什么必须平移：直接把 ankle 序列换成 box_bottom 会在信号上留下一个台阶，而**台阶本身会被当成一次起跳**，同时也会把真实起跳埋掉。补齐帧数记进 `stats["substituted_frames"]`，超过 30% 时审计给 `SIGNAL_SUBSTITUTED`。

### 6.6 信号源择优（`pick_source` / `source_scores` / `channel_quality`）

`signal_source="auto"` 时，不是一律优先脚踝：远景或小腿抬得低时踝位移只有一两个像素，一半真起跳落在阈值以下。做法：

1. 先按覆盖率筛掉可用帧不足 50% 的部位（`usable >= 0.5 × len(samples)`）；
2. 在剩下的踝/髋/头里，用 `channel_quality` 打分，取**节律强度**最高者；
3. 但挑战者必须比"覆盖率兜底源"明确胜出 `channel_switch_margin=0.08` 才换，避免两个通道打平时来回跳（换通道 = 信号台阶 = 假峰）。

**同清晰度档内改比"谁数得出的起跳多"**（`channel_prefer_rate_margin=0.15`，`counter.channel_rank`，离线在线同一函数）：

```
rank(通道) = (1 if 强度 >= 最强强度 - margin else 0, 过阈值峰数, 强度)   # margin>0
rank(通道) = (强度, 峰数)                                              # margin=0，历史口径
```

理由是纯比强度在**快跳人群**上会选错通道：快跳的人头颈几乎不动但信号很平滑，自相关强度反而压过踝，
于是选中的通道把一整段快跳数成十几次慢摆。实测两条证据：

- 机会成本（`out/tune/probe_channel.py`，逐条轨迹强制用踝/髋/头/框底边各数一遍）：
  被选中通道合计 4954 次，每条各取最优合计 5632 次，**机会成本 678 次（13.7%），涉及 76 条轨迹**；
- 典型样本 `179023428267 #18`：选头 → 周期 1.84s / 共 11 次，选踝 → 周期 0.32s / 共 69 次，
  时空图 `out/tune/st_179023428267_18_8s.png` 上是高频细纹（真快跳），不是慢摆。

换过来的峰是不是关键点抖动，用**他道作证率**核（`out/tune/probe_corate.py`：每一次起跳，另外两条通道
在同一时刻 ±0.25 周期内有没有鼓包）：快跳组（≥2.4Hz）作证率 90.2% → 换通道后 88.9%，慢跳组 72.6% → 71.8%，
**多出来的峰带着同等水平的佐证**，不是新引入的抖动。注意 `179023471330 #9` 这类作证率只有 25.8% 的老样本
是换通道之前就存在的，见第 12 节。

`channel_quality` 的判据与真正计数用的判据是**同一套**（同样的 detrend / 噪声 / 阈值 / 取峰 / 自相关），返回 `(节律强度, 过阈值峰数, 观测覆盖率)`。这是刻意的：否则会出现"选源时分数很高、真计数时一个峰都出不来"的错位。

节律强度定义（在线侧 `online.py` 同式）：

```
rhythm_strength = clip(1 - median(|峰间隔 - period|) / period, 0, 1)
```

`period_source == "fallback"`（周期没真测出来）时强制 `strength = 0`。

在线链路为了省时间，通道重选按 `channel_reselect_sec=1.0` 秒节流（三条通道得分逐帧几乎不变）。

### 6.7 信号预处理（`jumpcount/signal.py`）

顺序固定，不能换：

1. **缺帧插值** `fill_gaps(frames, values, max_gap=12)`：把稀疏观测铺成逐帧稠密序列，短洞（`<= max_gap`）线性插值，长洞计数 `long_holes`（审计据此报 `TRACK_FRAGMENTED`）。同时构造 `observed` 布尔数组——**后面所有"这段人到底在不在画面里"的判断都靠它**。时间轴同步插值（`times_dense`），否则亚帧峰对回秒数会错。
2. **中值滤波** `median_filter(values, smooth_win=3)`：去单帧离群点。窗口保持很小（3），因为"中值窗口一长，先没的总是小幅起跳"。
3. **去基线** `running_baseline` = 长度 `baseline_win=91` 帧（约 3s）的滑动中值，减掉它。作用是削掉相机抖动、人员身高差、透视漂移这类慢变化。序列不足 91 帧时用 `_odd(size // 2)` 兜底。

`detrend()` 就是 2+3 的组合，输出即 `detrended`，全流程唯一的"起跳信号"。

4. **带通只在能量包络分支里用**（6.12），主峰检测不在主链路上做带通，避免边界效应影响正常幅度大的峰。

`autocorr_period(x, fps, min_hz, max_hz)` 的搜索窗口是 `[max(2, int(fps / max_hz)), min(n-1, round(fps / min_hz))]`。
下界那一句**必须向下取整**，且与计数侧的 `hard_min` 同口径：它是自相关能看见的最短周期，向上取整等于把快跳整段挡在自相关的视野之外（见 6.10.1）。

### 6.8 噪声估计（`hf_sigma` / `hf_sigma_masked`）

阈值 = `snr_k × 噪声`，所以噪声估计算法直接决定灵敏度。

- `hf_sigma(values)`：一阶差分的稳健标准差 `1.4826 × MAD(diff) / sqrt(2)`。用差分而不是直接 MAD 的原因：起跳本身幅度很大，直接 MAD 会把起跳当噪声，阈值虚高。
- `hf_sigma_masked(values, observed)`：**只用连续真观测的片段**（长度 `>= 6` 帧）分别估，再取中位数。两条理由：
  - 插值补齐的段被拉平过，混进来噪声假性变小 → 阈值变松 → 抖动被数成起跳；
  - 缺口两侧那一帧的差分跨越了整段缺席（几十帧的位移差），混进来噪声虚高 → 阈值变严 → 小幅起跳被切掉。
- **离线与在线必须用同一口径**（在线原先用 `hf_sigma`，已统一改成 `hf_sigma_masked`，见 `online.TrackCounter.poll`）。两边口径不一致会让"实时比离线多/少"这类对比完全失去意义。
- `mad_sigma` 仅作参考记入 `stats["noise_mad"]`，不参与阈值。

### 6.9 计数阈值（`absolute_floor` / `amplitude_threshold`）

```
scale  = clip(median_h / amplitude_ref_height, amplitude_floor_min, 1)   # ref=260px, floor_min=0.35
floor  = min_amplitude × scale                                            # 2.0px × scale
thr    = max(floor, snr_k × noise, peak_frac × peak_level)                # snr_k=3.0, peak_frac=0.08
thr    = min(thr, max(amplitude_ratio × median_h × relief, 0.45 × peak_level))  # ratio=0.004
```

其中 `peak_level = percentile(detrended, 95)`，`median_h` 是该轨迹框高中位数，`relief = floor_relief`（默认 1.0）。

每条线的来由：

- `floor`（绝对像素下限）：拦机身抖动。**必须按框高等比缩放**——`min_amplitude=2px` 是给近景定的，16 人群像里中位框高 172px，真实离地在踝部只有 1~2px，不缩放就砍掉半数起跳。缩到 0.35 封底，不再往下。
- `snr_k × noise`：主判据。
- `peak_frac × peak_level`：峰必须显著高于整段幅值的一个比例，防止在整段塌陷时把噪声尖当成峰。
- 最后 `min(...)`：阈值不能超过信号本身，上限压在 `0.45 × peak_level`。下压时只压到"框高比例下限"，**不压回绝对像素下限**（否则 6.9 第一条缩放全白费）。
- **那条上限本身是个双刃剑**，已加开关 `threshold_cap_floor_frac`（默认 0 = 历史行为）：上限允许把阈值压到多低，`1.0` 表示不许低于绝对像素下限。
  平躺/站着的人信号只有 ±1px 时，上限会跟着落到 0.7px 附近，抖动全被当成起跳（`179023471330 #11`：全身最大位移 5.7px 却数到 29 次）。
  实测取 `1.0`：计入 4700 → 4666（−34），双计特征 2.48% → 2.19%、回捞自身双计 0.61% → 0.20%，但实时链路一次掉到 4532（−218）——
  这条上限同时是"远景小幅起跳"的救命索（阈值被抬高后 `#18` 那类快跳反而从 11 次变 69 次，方向正确，但 `179023484385 #22` 从 27 次掉到 2 次）。
  **净效果与"先把快跳数全"相反，暂不启用**，保留开关与逐条差分（`out/tune/tracks_cf_base.tsv` / `tracks_cf100.tsv`，日志 `out/tune/DOC_capfloor.log`）。
  头部零位移闸门同轮复核：`min_head_move_px 1.0 → 2.0` **完全无效**（那几条卡在占比条件 `head < 0.30 × body` 上，位移条件从不生效），
  `min_head_share 0.30 → 0.35` 只有 −6 次，两者都不动，见第 10 节。
- `amplitude_ratio=0.004`（框高的 0.4%）**看着太小但别再动**：它把阈值钉在亚像素，站着拿绳不动的孩子也能蹭到 9~23 次。曾试过抬到 `0.012`（与"明显离地"判据 `min_lift_ratio=0.012` 对齐），实测在抬脚比 ≥3% 的人群里也掉了 206 次，误伤真跳绳者，已否决（见第 10 节）。真正该修的是"框底边被前景行人带动"这类通道污染，不是把全局阈值抬高。

### 6.10 节奏（周期）估计：两遍法

自相关在人群素材上会把噪声尖峰当成周期（一次跳数成两三次），所以不直接用自相关结果：

```
hard_min = max(2, int(fps / max_rate_hz))                      # 物理上限对应的最小峰间隔(向下取整)
coarse   = find_peaks(detrended, hard_min, amp_thr, 0.8×amp_thr)
if len(coarse) >= 3 and fps/max_rate_hz <= median(diff(coarse)) <= fps/min_rate_hz:
      period_frames, period_source = median(diff(coarse)), "峰间隔中位数"
elif autocorr_period(...) 落在 [fps/max_rate_hz, fps/min_rate_hz]:
      period_frames, period_source = ac_period × fps, "自相关"
else: period_frames, period_source = fps / ((min_rate_hz + max_rate_hz)/2), "fallback"
```

`min_rate_hz=0.5`、`max_rate_hz=4.5`。

`period_source == "fallback"` 是一个强信号：**这个人自己的节奏没测出来**，于是 (a) 节律强度强制为 0，(b) 能量回捞整条分支不启用，(c) 按节奏补齐不启用，(d) 三态判定里所有"低置信计入"资格取消。即"节奏测不出来"退化成最保守的人工水平，而不是拿一个中间周期瞎猜。

`median(diff(coarse))` 用中位数：它天然容忍个别漏峰和个别多余峰。

#### 6.10.1 快跳的 2:1 锁相（为什么上限是 4.5 且必须向下取整）

`max_rate_hz` 不只是"合理性校验"，它同时是**取峰能力**的上限，一共四个作用点，**四处必须同口径**（都向下取整）：

| 位置 | 作用 |
| --- | --- |
| `counter.channel_quality` 的 `hard_min` | 信号源择优时统计节奏用的最小峰间隔 |
| `counter.count_track` 的 `hard_min` | 离线第一遍粗取峰的最小间隔 |
| `online.TrackCounter.poll` 的 `hard_min` | **实时链路**同样的一遍粗取峰 |
| `signal.autocorr_period` 的 `lo` | 自相关能看见的最短周期 |

**两条失效路径**（都源于上面这一个数同时兼任三份活：取峰器的最短间隔 `hard_min`、
验收闸门的下界 `fps/max_rate_hz`（**带小数**）、自相关的最短滞后 `lo`）：

- **路径 A —— 量出来的节奏卡在"取峰器拿得到、验收闸门不认"的缝里。** 旧配置 25fps 下
  `hard_min = round(25/3.5) = 7` 帧，而闸门下界是 `25/3.5 = 7.1429` 帧：整数间隔永远不可能既 `>= 7`（被取到）
  又 `>= 7.1429`（被验收）。真周期正好 7 帧（3.571Hz）的人，峰列一个不缺地取到 71 个、间隔中位数就是 7.0，
  却被判"不可信"；自相关的 `lo` 也是 7，同样够不着闸门 → 落到 `period_source = fallback`，
  节奏当作"测不出来"：估计频率退回区间中点 **2.0Hz**，节律强度归零，能量回捞与按节奏补齐**全部关闭**。
  峰取满了，次数只有一半。
- **路径 B —— 标准的 2:1 锁相。** 真周期短于 `hard_min` 时，不应期 NMS 把间隔不够的峰**隔一个吞一个**，
  量出来的间隔中位数直接翻倍（真 6.25 帧 → 量出 12 帧），12 `>= 7.1429` 顺利通过验收，
  于是估出 2.083Hz——**恰好是真实值的一半**，计数腰斩。

合起来就是"跳得越快反而数得越少"，而且掉得越来越狠：路径 A 把人打回 2.0Hz 中点，路径 B 把人打回半频。

合成实测（25fps、20s、14px 起跳，`计入` 含按节奏补齐；旧 = `max_rate_hz=3.5` + `round`，新 = `4.5` + 向下取整）：

| 真实频率 | 真间隔(帧) | 旧 `hard_min` | 旧·粗取峰数 | 旧·间隔中位(帧) | 旧·计入/真值 | 旧·`period_source` | 新·计入/真值 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 3.571Hz | 7.00 | 7 | 71 | 7.0 | 32 / 71 | **fallback** | 63 / 71 |
| 3.6Hz | 6.94 | 7 | 68 | 7.0 | 30 / 72 | **fallback** | 68 / 72 |
| 4.0Hz | 6.25 | 7 | 40 | **12.0** | 37 / 80 | 峰间隔中位数（= 半频） | 76 / 80 |
| 4.5Hz | 5.56 | 7 | 40 | **11.0** | 38 / 90 | 峰间隔中位数（≈ 半频） | 85 / 90 |

看 3.571Hz 那一行：旧配置**峰取满了**（71 个，一个不缺）却只数到 32 次——问题不在取峰，在验收闸门与取峰器口径不一致。

所以修法是两条，缺一不可：

1. **上限 3.5 → 4.5**：把 `hard_min` 与闸门下界一起降下来，覆盖到 25fps + `smooth_win=3` 还分辨得开的区间；
2. **`round` → 向下取整**：保证恒有 `hard_min <= fps/max_rate_hz`，**取峰器永远不会比验收闸门更严**，
   频率带顶端不会再出现"名义上允许、实际取不到"的空洞。

三重证据（工具与留痕都在 `out/tune/`）：

1. **合成扫频**（`out/tune/sweep_rate.py`，0.8~6Hz）：旧配置 ≤3.2Hz 达成率 0.94~0.96，**3.6Hz 起崩到 0.41~0.46，且估计频率恰为真实值一半**。
2. **不受任何上限约束的自相关**（`out/tune/probe_period.py`，判真伪周期的最终手段）：`179023428267 #2` 在滞后 7 帧 +0.79、14 帧 +0.61、20 帧 +0.53，半周期处 3~4 帧为 −0.35、10~11 帧 −0.53。相关曲线在 7 帧取最大、在 14 帧只是次谐波 → 真周期就是 7 帧。
3. **肉眼**（`render_track.py`）：`--st` 时空展开图上波纹与 3.57Hz 标记 1:1 吻合；胶片图里 `y` 读数（框顶纵向位置）逐帧摆动，波谷间隔 0.24~0.32s、幅度约 25px，脚确实每一拍离地一次。

改后的实测（同一份 YOLO 缓存，`out/tune/DOC_rate_floor_online.log`）：

| 配置 | 离线计入+低置信 | 实时链路 | 双计特征 | 回捞峰自身双计 | CV |
| --- | --- | --- | --- | --- | --- |
| `max_rate_hz=3.5` + `round`（旧默认） | 4101 | 4446 | 4.28%（152/3548） | 0.00%（0/306） | 0.662 |
| `4.5` + `round` | 4711 | 4672 | 2.45%（99/4036） | 0.00%（0/416） | 0.698 |
| `5.0` + `floor` | 4801 | — | 2.38%（99/4163） | 0.41%（2/487） | 0.716 |
| **`4.5` + `floor`（当前默认）** | **4844** | **4934** | **2.51%（106/4227）** | **0.41%（2/485）** | **0.712** |

（中间两行的实时列测于 `online.TrackCounter.poll` 那处 `hard_min` 尚未同步之前，与当前默认行不可直接相减；离线列与双计列可直接比较。）

离线 +18.1%、实时 +11.0%，而两条"数重了"的直接证据一条都没变差：双计特征从 4.28% **降到** 2.51%，
回捞峰自身双计只多了 2 个（0.00% → 0.41%）；虚高（> 1.05 预期）恒为 0 条，判为在跳绳的轨迹数不变（73）。
多出来的次数是本来就该数到的那一批，不是拆出来的。

**为什么不取 5.0**：合成 5.0Hz 时达成率已经掉到 0.39（`period_source` 落到 `fallback`），而回捞峰自身双计从 0 变成 0.41%——
`hard_min` 只剩 5 帧（0.2s），中值滤波（`smooth_win=3`）之后波形已经分辨不出单拍了。4.5 是当前 25fps 素材能守住"不漏"同时基本不"数重"的位置。
**已知边界**：真实频率 > 4.5Hz（270 个/分钟以上）仍然会锁相，解法不是继续调这个参数，而是提高输入帧率或换更短的 `smooth_win`。

回归测试：`tests/test_core.py::TestFastJumpNoPhaseLock`（3.6Hz 与 4.0Hz 达成率 ≥ 0.9，且把上限调回 3.5 必须重现腰斩）。

### 6.10.1 快跳自适应窄窗与节拍格子过滤（`analyze_signal` / `pick_smooth_pass` / `keep_on_grid`）

中值滤波窗口 `smooth_win=3` 是抗抖的主力，但它对快跳是致命的：快跳的一拍在踝部只窄到一两帧，
`median(0, 9, 0) = 0`，整拍被抹平，于是**跳得越快数得越少**。解法不是全局换成窄窗（全局 `smooth_win=1` 实测 +223 次，
但双计 3.08%、CV 0.735，把噪声一起放了进来，见第 10 节），而是**按这个人自己的节奏决定用哪一档**：

```
main = analyze_signal(smooth_win=cfg.smooth_win)          # 主档(宽), 走完去基线→噪声→阈值→粗取峰→节奏
若 main 频率 < smooth_fast_min_rate(2.0) 或 周期是兜底值 → 不换档
alt  = analyze_signal(smooth_win=cfg.smooth_win_fast=1)   # 第二档(窄)
换档条件: alt.峰数 ≥ smooth_fast_gain(1.15) × main.峰数
      且 alt.clarity ≥ main.clarity - smooth_fast_margin(0.05)
      且 keep_on_grid(alt.峰, main.峰) 之后 ≥ max(smooth_fast_min_extra=8, main.峰数)
```

`analyze_signal` 是把"去基线 → 噪声 → 阈值 → 粗取峰 → 节奏 → 清晰度"整条前段抽出来的纯函数，
抽出来才能用**同一份位移**跑两档窗口再比。

**格子过滤 `keep_on_grid` 是关键的收敛步骤**：窄窗多出来的峰里，只留两类——

1. 与宽窗实测峰是**同一拍**（距离 ≤ `recover_center_tol=0.35` × 周期，只差亚帧）；
2. 离最近实测峰正好 **整数倍周期**（`|dist − k×period| ≤ 0.35 × period` 且 `dist > 0.6 × period`）——这就是被滤波抹掉的那一拍，
   宽窗每少一半就出现一次 2:1 锁相。

离峰 0.43 个周期那种是抖动，丢掉。宽窗实测峰 < 4 个时不过滤（锚点不够，格子本身画不准，宁可原样放行）。
证据（`out/tune/probe_smfast.py`，日志 `DOC_smfast.log`）：17 条换窗轨迹多出 107 个峰，其中 **92% 踩在格子上**；
加过滤把双计特征从 2.72% 压回 2.48%。

**触发频率下限取 2.0 不取 1.5**（`out/tune/DOC_smfast_trigger.log`）：1.5 档能再多 122 次，但用他道作证率
（`out/tune/probe_corate.py`）逐条核对，被换的轨迹作证率从 ≥64% 掉到 27.9%（`179006213119 #11`），买来的峰没有旁证；
2.0 档 +23 次、双计特征反而降到 2.40%、快跳组作证率 88.9% → 87.9%，可接受。

新增状态量：`smooth_win_used` / `smooth_fast_tried` / `smooth_peaks_used` / `smooth_peaks_other` / `smooth_fast_dropped`。
回归测试：`tests/test_fast_track.py::TestKeepOnGrid`、`::TestOnlineFastWindow`。

### 6.11 峰检测（`signal.find_peaks`）

手写，不依赖 scipy。四步，顺序有意义：

1. 局部极大：`v[i] >= v[i-1] and v[i] > v[i+1]`（左边取 `>=` 让平台顶部只留右侧一帧）；
2. 幅度过滤：`v[p] >= amplitude`；
3. 突出度过滤：`v[p] - max(min(左侧), min(右侧)) >= min_prominence`（简化鞍点公式），调用侧统一传 `0.8 × amplitude`；
4. 不应期 NMS：按峰高降序贪心，保留的峰两两间隔 `>= min_distance`。

不应期：`min_distance = max(hard_min, refractory_ratio × period_frames)`，`refractory_ratio=0.6`。这个值调小的后果很明确：一次起跳被数成两个；调大的后果：真双摇被并掉。0.6 是实测可用值。

亚帧定位 `parabolic_peak`：对选中峰做三点抛物线插值，`frame_pos = axis[0] + sub`，再 `interp` 回时间轴。这让 `expected_count` 与间隔统计不被整帧量化污染。

#### 6.11.1 「落回地面」判据（`signal.merge_close_peaks`）

不应期是纯时间闸，快跳时它会连真起跳一起吃掉：25fps 下 3.6Hz 的真周期只有 7 帧，
而 `min_distance` 一旦被节奏估计的失误抬到 8 帧，取峰器就只能每隔一拍取一个，计数当场腰斩
（合成用例：`landing_valley_frac=0` 时 3.6Hz 在旧上限下只数到 42%）。

补一条物理判据，接管"这两个挨得很近的峰算几次"：

```
valley = min(values[prev : p + 1])                  # 两峰之间（含端点）的最低点
落地   = valley <= landing_valley_frac × amp_thr     # 用计数阈值本身量"落回地面"有多深
落地   → 两个峰都保留，并把 p 记进 landing 集合
没落地 → 合并成一个，保留更高的那只
```

* 起跳的物理形状是「腾空 → 落地 → 再腾空」；同一次起跳里绳过两次（双摇）时脚没有落地，
  谷底一直停在高位。所以谷底就是"算一次还是两次"的直接证据，比时间间隔可靠。
* **尺子必须是 `amp_thr` 而不是峰高**：纯噪声里相邻两峰之间"总能"凑出一个相对自己很深的谷
  （实测谷底/峰高中位数 ≈ 0.9 的分布会一路铺到 0.2），拿峰高当尺子等于给静止抖动发资格。
  用阈值之后，"落地"要求位移真的回到起跳阈值以下，与整条链路的其它门限同量纲。
* `landing` 集合必须一路带到事件分类：`double_under_ratio` 那条双摇判据用的是同一个时间间隔，
  不在这里网开一面，刚救回来的峰立刻会被当成双摇再扣一次，等于什么都没做。
* 候选来自 `coarse`（同一套阈值、只受 `hard_min` 约束），**没有引入新的门限**。
* 离线（`counter.count_track`）与实时（`online.TrackCounter.poll`）同一段逻辑、同一个参数。

回归：`tests/test_core.py::TestSignal::test_landing_split_keeps_two_real_jumps` /
`test_landing_merge_collapses_a_shoulder` / `test_landing_rule_uses_the_threshold_not_peak_height`，
以及 `TestFastJumpNoPhaseLock::test_old_three_and_a_half_cap_was_the_cause`
（关掉这条判据必须重现腰斩，开着必须救回来，两个方向都锁住了）。

### 6.12 能量包络回捞（核心新增，`signal.bandpass` / `signal.energy_envelope` / `signal.gap_candidates` / `counter.recover_peaks`）

**问题**：位移阈值这条路余量已用尽（6.9 已经把绝对下限压到信号封底），剩下的漏计是"真起跳但幅度整段压在阈值下"。继续松阈值先进来的是噪声。

**思路来源**：心电 R 峰检测（Pan-Tompkins / Hamilton，参考实现 NeuroKit2）。它面对的是同一个问题——真信号幅度跨度大、噪声与信号同带、漏一个就是一个计数、多一个就是虚假计数。它的解法不是"在原始波形上找峰"，而是**带通 → 微分 → 平方 → 滑动积分**，在"能量"上找，再用不应期 + 搜索回溯控制。同类跳绳计数公开仓库（MediaPipe/YOLO + 阈值规则）没有更聪明的判据；监督式动作计数（PoseRAC、Countix）需要重训权重，违反"用现有权重"的前提，均不采用。

**流水线**：

1. **零相位带通** `bandpass(values, fps, 0.7, 4.0)`：FFT 实现，通带内置于 `[lo, hi]`，两端各加 `ramp = max(0.05, 0.3×lo)` 的升余弦过渡，上限自动收到 `0.9 × Nyquist`。
   为什么 FFT 零相位而不是 scipy Butterworth + `filtfilt`：**不引 scipy** 且**不产生相位延迟**——相位一漂，峰位置整体错位，计数就整体错位。
   为什么带通优于再加一层中值：关键点抖动在高频、走动与透视漂移在低频，两端一起削掉比拉长中值窗口干净得多。

2. **能量包络** `energy_envelope = moving_average(diff(band)^2, win)`，`win = max(3, round(envelope_win_ratio × period_frames))`，`envelope_win_ratio=0.4`。
   两个作用：① 平方让"幅度小但整段同向"的相干运动相对噪声占便宜（噪声是零散差分，起跳是一整段速度）；② 滑动积分把一次起跳的**上升沿与落地沿并成一个鼓包**，从源头上把双计砍掉一半。

3. **候选提取**：
   - 正常档：`find_peaks(env, min_distance, env_thr, 0.8×env_thr)`，`env_thr = envelope_frac × percentile(env, 95)`，`envelope_frac=0.05`；
   - 逐档 search-back：`gap_candidates(env, cands, min_distance, env_thr, search_back_ratio × period_frames, search_back_levels=(0.5, 0.35))`
     只在"按节奏本该有起跳却没数到"的区间压低阈值——相邻实测峰之间空档超过 `search_back_ratio=1.66` 倍周期（沿用 R 峰检测经验值），以及**首尾两段**（信号整段塌陷时空档只有一侧有实测峰，早期版本一个都补不出来）。阈值先压到 0.5 再压到 0.35，取到就停。
   - **返回值必须是 `List[Tuple[int, float]]`（位置 + 取到它的那一档）**：复核时必须沿用同一档。踩过的坑——取候选时压到 0.35，投票却按原阈值算，弱起跳刚被捞出来又被票掉。

4. **落回原始位移** `refine_peak(detrended, cand, radius=max(1, round(0.4×period)))`：在包络峰附近取原始位移的最高点，**出数时刻与幅度都按原始位移报**（包络只负责"提名"，不负责"定值"）。

5. **四道闸依次签字**（顺序即代价从低到高；「节拍格」这一道拆成 A/B 两行写）：

   | 闸 | 判据 | 默认参数 | 治什么 |
   | --- | --- | --- | --- |
   | 观测率 | `mean(observed[pos ± min_distance]) >= recover_min_coverage` | 0.7 | 人不在画面里时不替他猜 |
   | 原始位移下限 | `value >= recover_raw_ratio × amp_thr` | 0.30 | 包络说是起跳不算数，位移上得真有个鼓包 |
   | 多通道同刻投票 | `votes(pos, level) >= envelope_lead_votes` | 默认 2 票。**计票方式**：被数通道自己的能量包络算 1 票，另外每条候选部位（踝/髋/头 中除去主通道，最多 2 条）各算 1 票；时刻容差 `envelope_lead_tol=0.35 × period`，每条通道的门槛 = `envelope_lead_frac(0.06) × 该通道自己的包络 p95 × level`。所以默认 `2` 的实际含义是「主通道 + 至少一个别的部位」 | 真起跳时踝/髋/头一起动，单通道抖动不会 |
   | 节拍格 A（不应期） | 与左右邻居的间隔都 `>= recover_gap_ratio × period` | 0.75 | 挤进 0.7 倍以内就是双计 |
   | 节拍格 B（踩格子） | 双侧空档：`|pos - (prev+nxt)/2| <= recover_center_tol × (nxt - prev)`；单侧空档：`||pos - anchor| - grid| <= recover_center_tol × grid`，`grid = median(diff(base))` | 0.35 | 站着抖的人也凑得出"空档"，这条专治幻影 |

   投票通道集合：`("ankle","hip","head")` 去掉主通道本身。每条通道先 `channel_on_axis` 搬到主通道的稠密帧轴（缺帧插值）——不搬到同一帧轴就没法比"同一时刻的鼓包"。

6. **候选之间二次去重**（必做，易漏）：`refine_peak` 之后位置会漂移 1~2 帧，可能落到某个实测峰身上。所以细化后要**再查一次** `any(abs(pos - known) < min_distance for known in accepted)`，命中就丢弃（同一次起跳，不是新的一次）；最后 `nms_by_height(detrended, accepted, min_distance)` 按原始位移高度统一做一轮 NMS。踩过的坑：没有中间这次复查时，最终 NMS 会把**实测峰**顶掉（因为回捞峰细化后原始位移值可能更高），导致总数不变但"把真峰换成回捞峰"，且 `recovered` 统计失真。

7. 事件层：回捞峰 `JumpEvent.recovered=True`；在线侧 `record["recovered"]=True`、`TrackCounter.recovered` 计数、`stats`/`snapshot` 都带 `recovered` 字段；页面卡片显示「+N 包络回捞」。

**验收指标**：回捞开启后 `count_track` 的结果必须 **单调不减**（`test_count_track_never_counts_less_with_envelope`），且**已有的实测峰一个都不能丢**。

#### 6.12.1 节拍格认领亚阈值鼓包（`counter.recover_grid_peaks`，`grid_fill_frac` / `grid_fill_clarity` / `grid_fill_tol`）

阈值这一侧已经没有余量（见 6.9），但有一类漏算整片卡在阈值下面：远景的人抬腿在踝部只有 0.3~0.7px，
而计数阈值由"框高比例下限"（`amplitude_ratio`）托底在 0.8px 左右。个案 `179023471330 #9`
（`out/tune/trace_one.py 179023471330 9`）：阈值 0.81px，57 个候选鼓包全在 0.3~0.7px 之间，节律强度却有 0.887 ——
信号很弱但节拍清楚得很，57 个鼓包恰好就是 57 次起跳。

于是换一条判据：**由"什么时候该有起跳"反过来决定"多小的鼓包算起跳"**。

```
phase  = median(已认峰位置 mod period)                    # 公共相位定出节拍格
for k in range(len(axis) / period):
    center = round(phase + k × period)
    跳过: 与任一已认峰的距离 < recover_gap_ratio × period   # 与包络回捞同一条防双计距离
    pos   = argmax(detrended[center-tol : center+tol])
    认领: observed[pos] 且 detrended[pos] >= grid_fill_frac × amp_thr
资格: 已认峰 >= 4 个 且 rhythm_clarity >= grid_fill_clarity(0.6)
```

概率解释是这条判据的全部底气：随机噪声踩到格子附近（±`grid_fill_tol`）的概率只有约 `2 × grid_fill_tol` ≈ 50%，
而真起跳**一定**落在格子上。`grid_fill_clarity=0.6` 比 `keep_rhythm_strength=0.35` 高一档，
因为这条是"拿幅度换确定性"，节奏不够硬就不该换。

扫档（离线总数 / 双计特征 / 节奏离散度，日志 `out/tune/R_grid_sweep.log`）：

| `grid_fill_frac` | 计入合计 | 双计特征 | 节奏离散度 CV | 说明 |
| --- | --- | --- | --- | --- |
| 0（关） | 5536 | 2.40% | 0.669 | 相位旁路之后的起点 |
| 0.2 | 5685 | 2.32% | 0.656 | 认领幅度 0.16px 已低于噪声 0.24px |
| **0.3（默认）** | **5656** | **2.33%** | **0.663** | |
| 0.5 | 5604 | 2.35% | 0.678 | |
| 0.65 | 5579 | 2.36% | 0.664 | |

取 0.3 不取 0.2：多出来的 29 次没有信号支撑；按"新增认领峰的他道作证率"算只有 **38.7%**，
与按节奏补数（39.0%）同级、低于包络回捞（43.1%）和实测起跳（65.4%），
已经贴着"信节奏不信信号"的边界（`out/tune/probe_phaseproof.py`，日志 `R_phaseproof.log`）。要更激进就调 0.2。

与包络回捞的分工：包络回捞是**先在信号里找一个鼓包**、再用节拍验身份；认领节拍格是**先相信节拍**、
再到格子上取最大的鼓包。两者共用同一条防双计距离（`recover_gap_ratio`）与同一条观测判据（`observed[pos]`）。

三条接线纪律：

- 认领出的峰计入 `stats["recovered_grid"]`，**不**打 `recovered` 标记 —— `recovered` 是包络回捞的口径，
  混用会让"回捞自身双计率"这条护栏失去可比性。
- 实时侧必须接在 `rhythm_clarity` 算完**之后**（`online.py`）：认领来的峰不能反过来给"节奏清不清楚"作证，
  否则一条轨迹能靠认领把清晰度抬上去再领更多（自我循环）。离线侧同理接在 `clarity` 定完之后。
- 实时端不接这条就会比离线复盘少数一截：只改离线时离线 5656 / 实时停在 5247（日志 `out/tune/R_grid.log`）。

回归：`tests/test_core.py::TestUndercountRecovery::test_grid_peaks_claim_blurred_jumps_below_threshold`。

### 6.13 事件分类与按节奏补齐（`count_track` 尾部 / `online.update` 同构）

对峰列按时间顺序遍历，用间隔 `gap`（亚帧精度）与 `period_frames` 比较：

- `gap < double_under_ratio × period`（0.62）→ `kind="bump"`，**起跳口径不计数**，过绳口径 +1。这是双摇的判据。
- `gap > gap_ratio × scale`（1.5；`scale` 是**局部尺子**，见 6.13.1）→ 疑似漏计，`estimated_misses += round(gap/scale) - 1`。其中：
  - 若该区间 `mean(observed) < min_fill_coverage`（0.7）**且**相位对不上（见 6.13.3）→ 记入 `misses_unobserved`（**真漏计，不可补**，人本来就不在画面里）；
  - 若空档**内部**连一点离地证据都没有（见下"补齐的证据闸门"与 6.13.2 的多通道取证）→ 记入 `fill_no_lift` 并计入 `misses_unobserved`，**不补**；
  - 否则若 `interpolate_gaps=True` 且 `round(gap/scale) >= 2` 且 `rhythm_trusted` → 按等分位置插入 `min(expected-1, max_fill_per_gap=3)` 个 `kind="interpolated"` 事件，`confidence=min(0.9, 证据比)`（走相位旁路时取 `1 − 相位残差`），`amplitude=0.6 × amp_thr`，最后再受 6.13.4 的两条配额护栏削减。
- 其余 → `kind="jump"`，正常计数。

`rhythm_trusted = (period_source != "fallback") and (rhythm_strength >= keep_rhythm_strength=0.35)`。

四个封顶条件的作用：`max_fill_per_gap=3` 防止节奏估歪时整段虚高；`min_fill_coverage=0.7` 与回捞的观测率闸同源，保持"不替不在画面里的人猜"这一条纪律一致；`rhythm_trusted` 保证瞎猜周期时绝不补数；`fill_min_lift_frac` 保证"人停下没跳"时不凭空加数。

**补齐的证据闸门**（`counter.gap_lift_evidence`，离线在线同一函数，`fill_min_lift_frac=0.35`）：

```
skip  = max(1, round(0.4 × period_frames))          # 掐掉两侧起跳自己的上沿
inner = detrended[lo+skip : hi-skip]
inner.size < 3            → inf（空档太短，不拦：最多补一个，拦下来省的比亏的少）
max(median_filter(inner,3)) < 0.35 × amp_thr → 不补，记 fill_no_lift
```

不掐尾巴判据恒真——区间最大值永远是上一拍起跳自己身上沿。目视复盘：`179023471330 #2` 的跳者在 12.6s 后停下弯腰，位移掉到阈值以下，
补齐却照样在 12.80s / 13.05s 各造一次起跳，这就是"没跳也被计数"的来源；同时时空图 `out/tune/st_179006213119_11_24s.png` 那种纹理平稳的段落，
人确实没跳。开闸实测拦下 237 处空档 / 435 次未补，计入 4857 → 4636；被拦空档的内部证据≈0，判据与现象一致。
闸门开后再把 `max_fill_per_gap` 从 2 放到 3，找回 +66（4634 → 4700）且双计特征与间隔离散度都不变——**这两项是配套改动，单独放 3 会虚高**。
`fill_min_lift_frac` 扫过 0.2（+59，证据太薄）与 0.6（−93，过严），取 0.35。

#### 6.13.1 两把尺子：全局周期管取峰，局部快尺管该不该补

一条轨迹里的节奏会漂：实测起跳间隔的 lag-1 自相关 +0.31，115 条里 61 条 >0.25，50 条前后三段的间隔差 ≥50%。
拿全局周期当尺子，人后半段快起来时每段间隔都"没超过 1.5 倍全局周期"，于是既不进补齐、也进不了回捞的视野 ——
这是"跳得快就少数"的另一半原因（前一半是取峰上限，见 6.10.1）。

解法是把两件事拆开：`local_period_window=8` 取最近 8 个间隔的 `local_period_quantile=10` 分位数当**局部快尺**，
**只用于**"这一格该不该有起跳 / 该补几个"的判断；取峰间距与不应期仍按全局周期，
免得局部尺一短就把一次起跳的余振数成两次（双计特征会立刻涨）。两个细节别漏：

- **分位数取低不取中**：间隔序列只会因漏计变长、不会因漏计变短，所以低分位数才是"这一拍有多长"的无偏估计。
  扫档 50 → 4853、25 → 4905、**10 → 4961**（离线），且补数的他道作证率不降（45.9% → 45.6%，`out/tune/probe_fillproof.py`）。
- **进窗口的只有"当作正常拍收下"的间隔**（`gap ≤ gap_ratio ×` 全局周期）。漏计造成的双倍间隔一旦进桶，
  中位数被拉长，尺子反过来变钝 —— 实测比不改还少 208 次。

#### 6.13.2 取证从"只看主通道"改成"第 N 高的通道"（`gap_evidence_signals` / `gap_evidence_votes`）

原闸门只看被选中的那一条通道。远景的人被前排挡住时踝部只剩 1~2px，而头部/框底边还在明显起落，
闸门在踝部量不到鼓包就判成"他没跳"。现在判据换成**第 `fill_evidence_votes` 高的通道证据比**：

```
证据比(通道) = gap_lift_evidence(该通道去基线) / 该通道自己的阈值     # 阈值必须各算各的
证据        = 各通道证据比降序排列后取第 N 高                        # N=1 任一通道达标即补; N=2 至少两条同时达标
取证通道    = ("ankle","hip","head","box_bottom") 去掉主通道本身
```

- 各通道阈值按自己的噪声与幅度算（与 `channel_quality` 同口径）。直接套主通道阈值会把幅度天然更小的通道一律判成"没离地"。
- 滤波窗口跟住实际生效那一档：快跳换到窄窗时取证也按窄窗，否则被抹平的起跳在取证里同样找不到。
- **不含 `box_center`**：它与 `box_bottom` 同源，一起投票等于同一个观测算两票，2 票闸门形同虚设。

为什么该放开（`out/tune/probe_ev.py`，日志 `out/tune/R_ev.log`）：被原闸门拦下的 450 次空档，
其"最大通道证据比"分位数是 `[0.66, 1.49, 2.77, 4.41]`（中位数 1.49 早就在阈值之上），
而这些被拦空档的他道旁证率 **93%**，与已经放行那批的 **94%** 持平 —— **拦掉的不是猜，是漏**。

扫档（离线总数，配 `fill_cap_expected=True`，日志 `out/tune/R_votes_cap.log`）：0 票 → 4951、**1 票 → 5170**、2 票 → 5110、3 票 → 4981。
取 1 票时双计特征 2.40%、回捞自身双计 0.39%、CV 0.669 三条精度护栏一格没变，代价是离线计数多 0.3 ms/帧。
**`fill_evidence_votes=1` 与 `fill_cap_expected=True` 是配套改动**：只放取证不加配额上限，总数能到 5193 但会冒出 2 条虚高。
要更保守就调 2 票（少 60 次）。回归：`tests/test_recovery.py::TestGapFillEvidence`。

#### 6.13.3 遮挡空档改由相位连续性签字（`fill_hole_phase_tol`）

缺口归因（`out/tune/probe_hole.py`，日志 `out/tune/R_deficit.log`）把起点那 2147 个缺口分成四类：
未观测 967（37%）、**覆盖率够但取证被拒 961（37%）**、首段 439（17%）、尾段 228（9%）。
"未观测"这一类过去被 `min_fill_coverage` 一票否决，但遮挡空档内部的位移是插值填出来的，
离地取证闸门在这种数据上也量不出东西 —— 两条判据同时失效，这段就永远补不回来。

于是改由**相位连续性**签字：若 `gap / scale` 与整数的偏差不超过 `fill_hole_phase_tol`，
说明出洞后的第一拍仍然落在起跳前的节拍格上，人被挡住的那段时间节奏没有断，他确实还在按同一节奏跳；
中途真停下来的人，出洞后的第一拍必然落在格子外面。

```
residual  = |gap / scale − round(gap / scale)|
phase_ok  = fill_hole_phase_tol > 0 且 expected >= 2 且 coverage < min_fill_coverage
            且 residual <= fill_hole_phase_tol
放行条件   = 原来被 (coverage 不足 或 无离地证据) 拦下的空档, 只有 phase_ok 才补
```

**`coverage < min_fill_coverage` 这个限定是命门**：人站着没跳的那段位移是平的但一直在被观测，
两端峰的距离常常正好是整数个周期（residual≈0），不加限定就会把"没跳"判成"节奏没断"而凭空补好几个
—— `tests/test_core.py::TestUndercountRecovery::test_absent_person_is_not_backfilled` 抓到过，
修法是给该用例补一段"回来时脱拍"（`_samples(delay=7)`），而不是放宽闸门。

扫档（离线总数，日志 `out/tune/R_phase_tol.log`）：0 → 5193、0.15 → 5417、**0.25 → 5536**、0.35 → 5643、
1.0（等于不验相位）→ 5790 但虚高从 2 条涨到 3 条。取 0.25 的理由与 6.12.1 同源：
随机噪声踩中格子的概率约 `2 × tol`，放到 1.0 就是彻底放弃这道判据，多买 254 次却买不回精度。
旁路补出的次数单独记 `stats["fill_phase"]`（实时侧 `record["phase_filled"]`），
汇总侧 `summary["filled_by_phase"]`。回归：`test_absent_but_on_beat_gap_is_backfilled`。

#### 6.13.4 补数的两条配额护栏（取更严的一条）

取证与旁路都放开之后补数会变多变密，所以加两条总量护栏（都只削 `kind="interpolated"` 事件，
超配额时按 `confidence` 留强去弱，剩下的仍按时间顺序留在事件流里）：

| 护栏 | 参数 | 判据 | 作用 |
| --- | --- | --- | --- |
| 占比护栏 | `max_fill_share=1.0` | 补出的次数 ≤ 实测起跳数 × 该比例 | 防"补"反客为主 |
| 节奏应有上限 | `fill_cap_expected=True` | 补完后总次数 ≤ `⌈(可见时长 − warmup) ÷ 尺子⌉ − 已数到的次数` | 保证"补"永远不可能超过"一直不停跳" |

- 占比护栏**只对实测起跳 ≥4 次的轨迹生效**：远景被遮挡的人本来就数不出几个峰、全靠补数达标，
  对他们套比例等于把整条抹掉（实测在跳绳 70 → 69）。扫档 0.25 → 4693、0.5 → 4825、0.75 → 4928、**1.0 → 4961**，
  取 1.0 只拦"补的比实数还多"的病态轨迹，正常轨迹碰不到。
- 应有上限的**尺子必须取 `min(全局周期, 局部快尺)`**：全局周期被 2:1 锁成两倍时，按它算的预算只有真实拍数的一半，
  快跳的人会被这条上限整个卡死不补 —— 那恰好是最需要补数的场景（实时侧实测 5086 → 5054，见 6.15）。
- 实时侧算预算时要先减掉**离场寄存接回来的次数**（`carry_count`）：那部分发生在画面之外，不该占这段画面的预算。
- 被削掉的笔数记进 `stats["fill_capped"]`，汇总侧 `summary["fills_capped"]`。
  回归：`test_backfill_is_capped_per_gap`（该用例先关掉节拍格认领，否则认领路径先接住这几拍，量不到配额）。

**实测数与补齐数分两笔记**（`count` 与 `filled`）：混在一起会让灵敏度滑杆失去意义（门限再严也能靠补数追平），复盘时也看不出哪些是真抓到的。

在线版本额外处理：`last_peak_frame` 记录"上一个评估过的峰（含热身期被跳过的）"作为空档参考点。不记这个的话，热身期跳过的峰会被下一个峰当成一整段漏计补回来。

### 6.14 三态参与判定（`participation`）

区分"在跳绳的人"与"路过的人/站着抖的人"。三态而非二态：`in` 计入 / `provisional` 低置信仍计入 / `out` 剔除。

一票否决（`out`）的硬指标：

| 判据 | 阈值 | 理由 |
| --- | --- | --- |
| `duration_sec < min_track_sec` | 2.0s | 观测太短 |
| `excursion_ratio > max_excursion_hard` | 2.5 倍身高 | 再怎么同步也不可能是原地跳，多半是 ID 在不同人之间来回跳 |
| `lift` 和 `lift_ratio_best` 都 `< min_lift_ratio` 且节奏不清楚 | 0.012 | 没有明显离地 |
| `ankle_sync < min_ankle_sync` 且启用姿态判据 | -0.10 | 左右脚负相关 = 交替迈步 = 走路 |
| `height_cv > max_height_cv` | 0.18 | 框高忽大忽小 = 这条轨迹在不同人之间跳 |
| `head_p95_px < min_head_move_px` **且** `head_p95_px < min_head_share × body_p95_px` | 1.0px / 0.30 | 头一直不动 = 身体没整体离地，见 6.14.1 |
| `visibility < min_track_visibility_floor` | 0.25 | 看得见的时间太少 |
| `total_count < min_count_provisional` | 2 | 偶然抖出来的一两个峰（这里数的是实测 + 按节奏补齐的总证据，不只看实测） |

降级为 `provisional`（**计入总量**，但审计与页面标出来）：`excursion_ratio > 1.2` 但节奏清楚**且** `ankle_sync >= min_ankle_strong=0.85`；`lift < min_lift_ratio` 但节奏清楚；`visibility < min_track_visibility=0.5` 但 `>= 0.25` 且节奏清楚；`min_count_provisional <= count < min_count_active=5` 但节奏清楚。

**`rhythm_is_clear()` 是"能不能原谅幅度小/遮挡多"的唯一凭据**：真跳绳的人节奏一定清楚，路人抖出来的峰对不上任何固定周期。所以它同时是补齐资格、回捞资格、低置信资格三处的开关。

横向位移的正确算法（`drift_spread`）：**逐时间窗口量活动范围取中位数**，而不是整段取分位数。

```
win = max(3.0, drift_window_sec × fps)            # 3s
按窗口分箱，每窗取 P90 - P10，最后取各窗中位数
```

用整段分位数的失败模式：只有一帧被认成隔壁的人（ID 漂移），全程范围就炸成"走了两三个身位"，原地跳的真人被当路人剔除——这是早期少数（漏计）的主因之一。真在走动的人每个窗口都在移动，窗口中位数照样大；抖动只影响个别窗口。

`robust_spread`（P5~P95，用于 `bottom_spread_ratio`）同理，不用极差。

`lift_ratio_best = max(各通道的 P95(detrend) / median_h)`：脚踝抬得少时，头/髋/框底边能反映真实离地高度，避免因主通道恰好选了脚踝而误判"没离地"。

`ankle_sync`：左右脚踝 y 坐标的皮尔逊相关系数，需要 `>= 20` 个双方都可见的帧。在线版用增量矩（`sync_n/a/b/aa/bb/ab`，`>= 25` 帧才出值），避免在线链路只能剔除不能降级。

#### 6.14.1 头部零位移闸门（`min_head_move_px` / `min_head_share` / `min_head_coverage`）

`count_track` 里 `channel_lift_p95()` 会对踝/髋/头/框底边**各跑一遍去基线**并留下每条通道自己的
位移 p95 与观测覆盖率；`lift_ratio_best`（择优用）与 `head_p95_px` / `body_p95_px`（闸门用）
共用这一趟计算，所以这道闸门**不额外花算力**。

要拦的是这一类假节律：`179023471330 #12`，93 次、3.57Hz、信号取自踝部，
踝部位移 p95 = 4.7px 看着像在跳，而**头部位移只有 0.85px**、踝-头相关 -0.14。
肉眼核对胶片确认：那是站在场边拿绳的观众，前景行人经过时把框底边和踝一起带出了波纹。
真跳绳者全身一起离地，头部必然跟着抬。

判据是两个条件的合取，刻意收窄：

```
head_p95_px < min_head_move_px(1.0)                       # 头部读数在亚像素级 → 身体根本没离地
  且 head_p95_px < min_head_share(0.30) × body_p95_px      # 同时还要"只有局部在动"
  且 头部通道观测率 >= min_head_coverage(0.6)               # 头被挡住时不启用（读数为 None 直接放行）
```

* `body_p95_px` 只取踝/髋/头三条**身体通道**的最大值，不含框底边：框底边正是最容易被阴影和
  前景带动的通道，让它进"全身最大"等于让假节律自己作证。
* 单看「踝-头相关性」会误杀真跳绳者：`179023428267 #2` 真跳 117 次，相关性却只有 0.09。
* 单看「头部亚像素」也会误杀：远景 + 低抬腿时全身读数本来就都在 1~2px，此时
  `head / body ≈ 1`，占比条件不成立 → 放行
  （`tests/test_core.py::TestParticipantGate::test_subpixel_head_that_is_the_biggest_mover_passes`）。
* 阈值不敏感：`min_head_move_px` 取 1.0 / 1.2 与 `min_head_share` 取 0.25 / 0.30 四档结果逐格相同
  （都剔同样 10 条轨迹 / 122 次），闸门落在平台区而不是刀口上。
* 实时链路同判据：`channel_quality()` 多返回一位"该通道位移 p95"，`TrackCounter._head_p95()` /
  `_body_p95()` 复用通道择优那一趟（每秒一次）算出的分数，不在每帧重跑去基线。

闸门命中 6 条轨迹 / 115 次（`out/tune/probe_gate.py`，台账 `out/tune/DOC_gate_audit.log`），
在跳绳人数 73 → 70。**这是精度的收益而不是召回的损失**：那 115 次本来就不该计。
近门槛的 8 条 / 100 次也一并留在台账里（头部位移 1~2px、占比 0.3~0.6），把它们一起剔掉要连带牺牲真跳者，
`min_head_move_px 1.0 → 2.0` 实测**一次都不生效**（这几条卡在占比条件上），`min_head_share 0.30 → 0.35` 只 −6 次，两者都不动。

回归：`tests/test_core.py::TestParticipantGate` 的
`test_head_that_never_lifts_is_rejected` / `test_head_moving_with_the_body_passes` /
`test_missing_head_channel_is_not_evidence` / `test_subpixel_head_that_is_the_biggest_mover_passes`。

### 6.15 在线链路与离线的差异（`jumpcount/online.py`）

每人一个 `TrackCounter`，滑动窗口 `window = max(baseline_win × 3, fps × online_window_sec)`（默认 12s）。每帧 `observe()` 累积特征，按 `poll_hz=6`（每 6 次帧调用做一次峰值搜索；信号仍逐帧入队，**不会漏峰**）出数：

- 窗口内重跑 6.7~6.12 全流程（含包络回捞，通道缓冲独立于主通道）；
- **快跳窄窗也接了实时**（`online_fast_window=true`，`online.py` 调同一个 `pick_smooth_pass`）：
  离线复盘早就两档都跑，实时端一直只用宽窗，于是"实时比离线少数"——快跳在页面上先被抹平，离线再准也只是修历史。
  单独开关实测实时 4761 → 4785（+24），双计特征与回捞自身双计不变差，代价是实时链路 4.1 → 4.4 ms/帧（+7%）。
  只取窄窗档的 `detrended / noise / peak_level / amp_thr / coarse`，**周期仍用实时自己的峰间隔中位数**（含"作废"规则），不换节奏口径。
  关掉即退回"只用 `smooth_win` 一档"。回归：`tests/test_fast_track.py::TestOnlineFastWindow`。

* **节拍格认领与补数的三条判据也已接到实时**（`online.py`，与离线同一批函数）：
  `recover_grid_peaks()` 接在 `rhythm_clarity` 算完之后（认领来的峰不得反过来给自己的节律作证）、
  空档取证走 `gap_evidence_votes()`、遮挡空档按 `fill_hole_phase_tol` 放相位旁路、
  补数受 `max_fill_share` 与 `fill_cap_expected` 双护栏。漏接任何一条，实时都会比离线复盘少数一截：
  只改离线时离线 5656 / 实时停在 5247（`out/tune/R_grid.log`），全部接完 5303（`out/tune/R_round9.log`）。
  **配额上限的尺子必须与离线同源**：取 `min(全局周期, 局部快尺)`。只用全局周期时，
  它被 2:1 锁成两倍的轨迹会拿到只有真实拍数一半的预算，快跳的人被这条上限整个卡死不补（实时 5086 → 5054）。
- **确认延迟** `guard = max(smooth_win + 2, round(period))`：峰必须已经完整下落才承认，否则窗口边界抖动会造成重复计数。实时延迟因此约等于一个跳跃周期（120ms 量级），这是有意取舍；
- **出数最小间隔** `min_emit_gap = max(2, round(0.5 × period))`：窗口滑动会让同一个峰的帧位置漂移 1~2 帧，没有这道闸会重复出数；
- 断档 `> max_gap` 帧时 `_close_segment()` 并清空缓冲：人离场或长时间遮挡后另起一段，**不把缺席时间算进可见率分母**（否则可见率永远上不去，判定全线误剔）；
- 参与判定用累计量在线算，走动的路人当场标出来；`snapshot()` 每个通道/判定字段与离线同名，前端一套渲染。

两条"资格会过期"的规则（实时链路特有的坑，离线整段复盘不会暴露）：

- **节奏与节律强度会作废**（`tests/test_core.py::TestStaleRhythm`）。`period_frames` 与 `rhythm_strength` 只在"这一窗口里数到 ≥3 个峰"时才更新，早期版本从不清零：人早就停下不跳了，`rhythm_strength` 还停在 1.0，`period_source` 还是"峰间隔中位数"，于是"节奏清楚"的资格继续发放——低置信计入、按节奏补齐、包络回捞全都据此继续给他加数。现在窗口装满（约 12s 信号）却数不出 3 个粗峰时，`period_frames` 退回兜底值、`rhythm_strength` 置 `None`，`rhythm_is_clear()` 随即判假。
- **离场寄存**（`config.bank_counts`，`tests/test_core.py::TestAwayAndReturn`）。失联超过淘汰窗口（`max(max_age × 4, slot_keep_frames)` = 250 帧 ≈ 10s）后 `TrackCounter` 会被回收，原先连同已经数到的次数一起丢掉：页面总次数会倒退，出去喘口气回来的人从 0 重新开始。回收时把累计量按**站位**寄存进 `OnlineCounter.bank`（`bank_keep_sec=120s` 内、`bank_max=32` 个站位、按最久未用淘汰），下一个人**站在同一个圈里**新开轨迹时按 `slot_dist_ratio` / `slot_height_ratio` 认领并接回累计量。只有参与判定为"计入/低置信计入"的人才有资格寄存（走过去的路人抖出的几个峰不能替下一个人在数），且认领时那个位置当下不能有别人在跳。只接累计量，**不接**可见率/双脚同步性/信号窗口：接回来的必须是这个人自己的新证据。快照里 `carried` 字段单独标出接回了多少，页面卡片标题写明"含上一次离场前的 N 个"。

`engine.snapshot()` 另有两条口径说明：`total` 只累加 `participant=True` 的人，`total_excluded` 单列"暂停超过一个信号窗口、数到的次数还在他身上但暂未计入"的部分（对应第 9 节"剔除但仍数到 296"这个指标），页面上总次数掉下来时Tooltip 有地方解释，不必怀疑计数丢了。

`engine.Engine` 的实时主循环是**单线程串行**：`cap.read()` → 检测 → 跟踪 → 在线计数 → 缩放+画框 → JPEG 编码 → MJPEG 出流。已知问题：摄像头场景下 `read()` 与出图互相拖累，延迟单调累积（浏览器侧会把看不过来的帧攒在手里越拖越久，所以现在有 `stream_fps` 限流 + 先缩小再叠加）。这是当前最大的架构性待办，见第 12 节。

### 6.17 实时服务层的约束（`jumpcount/engine.py` / `server.py` / `web/app.js`）

这一段不影响计数精度，但决定了"页面上看到的数是不是后台真实的数"，复现时同样容易踩：

- **控制指令必须校验**。`KNOWN_ACTIONS = (reset, pause, resume, source, config, status)`；未知指令与未知配置项由 `LiveEngine.control` 抛 `ValueError`，`server` 转成 HTTP 400 + 中文原因。此前拼错的指令会被静默吞掉，页面显示"设置已生效"而后台一动没动。`_checked_config_value()` 同时拦住越界取值（`imgsz` 160~3840、`conf` ≤0.95、可见率 0~1、时间类必须 >0），否则一个 `imgsz=10` 就能让整段计数变成噪声。
- **前端要按返回体判成败**。`fetch()` 在 HTTP 400 上照样 `resolve`，只 `catch` 网络异常等于永远以为成功。现在 `control()` 检查返回体的 `error` 字段，报错在状态条上保留 4 秒，不被下一轮 500ms 轮询刷掉。
- **滑杆读数从服务端回流**。`snapshot()` 必须同时给出 `policy / signal_source / imgsz / conf / sensitivity / snr_k / min_track_visibility / min_track_visibility_floor`，前端 `syncControls()` 拿它们对齐控件（拖动中的控件不覆盖）。少一个字段，刷新一次页面就和后台错位一次，而且看着像"参数被重置了"。
- **换画面源是一次显式操作**：解除 `paused`（否则暂停中切源，页面永远等不到新帧），并把帧号、分段耗时、出图节拍一起归零（`StageTimings.reset()`）。否则页面上的秒表和"每帧多少毫秒"仍是上一个源攒出来的平均值，排查卡顿会被带到别的段上去。`StageTimings` 单独成类就是为了让这条可测（`tests/test_engine.py::TestStageTimings`）。
- **目录扫描不许 500**。`list_sources()` 里 `listdir` 与 `getsize` 之间文件可能被拷走，取失败就跳过这一条，而不是让整个 `/api/sources` 报错、页面下拉框白屏。
- **画面去重不等于计数去重**。`_hide_duplicate_boxes()` 只作用于叠加层；计数列表原样保留，否则替他保管次数的人一被去掉，总计立刻少一截。
- **三处数字必须同口径**：页面顶部总计、卡片主数字、叠加层框上数字与底部"总计"，全部是 `count + filled`。标注视频（`render.draw`）里被剔除的路人画灰框且不带数字，`pipeline.counted_track_ids()` 与 `counts.json` 用同一批人算总量。
- **打不开画面源要分摄像头和文件**。`LiveEngine._bind_wait()` 只对摄像头编号（`_is_camera()`）在 `BIND_RETRY_SEC=10s` 内有界重试——摄像头刚被别的程序占用、系统还没交出来、跑到一半掉线，都只是 `isOpened()=False`，一次就放弃等于让整场计数就此停摆。文件源**不重试**：路径写错时多等十秒只会让人以为程序卡住了。`MAX_STUCK_BINDS=3` 治另一半：能打开却一帧都解不出来的坏源，无限重开会变成满速空转，CPU 全烧在反复打开文件上，靠"本次打开后是否真读出过帧"（`read_since_bind`）识别。这三个值是类常量而不是配置项，因为它们只管"最多等多久"，与计数精度无关。
- **切画面源失败必须把上一个源开回来**。切换分支里旧捕获器已经 `release()`，若新源打不开就继续往下跑，下一帧是在空捕获器上 `read()` → 立刻"读到结尾" → 走循环重开把计数清零，页面看着像"换源把我的数换没了"。现在失败时立刻重开原源，并把原因留在 `switch_error`：`state["error"]` 会被下一帧清掉，页面根本来不及看到。
- **前端下拉框也以服务端为准**。`syncControls()` 只在 `#source` 的候选项里真有这个值时才回写，切源失败时选择会自己弹回真正在播的素材；用户刚点下去还没落地的那次用 `state.sourcePending` 挡住，否则每 500ms 轮询会让选择来回闪。`switch_error` 单独进"提示"列表而不是状态条，状态条会被下一轮轮询刷掉。
- **采集线程停了，`/stream` 必须自己收手**。`feeding()` 表示采集线程还在不在。采集线程因为报错退出后 `stop_flag` 并不会置位，拉流循环原来会永远睡在那条连接上；浏览器对同一主机的并发连接只有 6 条，攒下一堆再也等不到帧的死流，整个页面会连 `/api/state` 都发不出去。现在空闲超过 `STREAM_IDLE_SEC=3s` 且 `feeding()` 为假就断开，回归用例是 `tests/test_engine.py::TestStreamConnection`（真起一个 `ThreadingHTTPServer` 收一条流：死流要在 2 秒内自己关闭，还在出帧的流不许被当成死流关掉）。
- **素材列表要真的会重试**。`/api/sources` 失败时页面提示"稍后自动重试"，那就必须重试：`maybeLoadSources()` 失败后 2s 一次、正常 5s 一次重扫目录，素材往文件夹里一丢就能看到，不用刷新页面。列表内容没变就不重建 DOM（`state.sourceIds` 比对），否则用户正在选的那一项会被刷掉。素材名里的 `< & "` 一律 `esc()` 转义后再拼 `<option>`，不然一个带引号的文件名就能把整个下拉框结构弄坏。

### 6.18 摄像头采集层（`engine.FrameFeeder` / `_keeps_counts_on_restart`）

主循环原来是单线程的 `read → 推理 → 跟踪计数 → 出图`。视频文件这样没问题（帧由我们自己拉，多慢都不影响计数），但**摄像头的出帧节奏由设备定**：这一环比 30fps 慢，帧就在驱动队列里越积越多，页面画面越走越晚、延迟单调累积，屏幕上数的其实是几十秒前的人，而且没有任何地方能看出落后了多少。

- **取帧拆成独立线程，队列长度恒为 1**。`FrameFeeder` 一直从驱动读帧并**覆盖**同一格，主循环每次拿到的都是当下最新一帧；没被取走的旧帧直接丢。`dropped()` 就是"被覆盖掉的帧数"，它持续上涨说明推理跟不上摄像头的帧率。暂停时主循环不再取帧、线程继续覆盖同一格，恢复后拿到的是当下这一帧——原来暂停三十秒再恢复，页面要先花三十秒把攒下的旧帧补播完才回到实时。
- **文件源不走这条路径**（`_bind` 里只对 `_is_camera(source)` 生效）。计数用的是原始帧，覆盖式取帧等于把中间的帧丢掉，直接少数。回归用例 `TestFrameFeeder.test_a_consumer_that_keeps_up_sees_every_frame` 锁住"跟得上节奏时一帧不少"，`test_a_burst_collapses_into_one_slot` 锁住"挤在一起的帧只留最新一帧"。
- **`CAMERA_READ_TIMEOUT = 3.0s`**：等摄像头交出下一帧的上限。超时按"采集停了"处理，让主循环去重开画面源，摄像头被拔掉不会把主循环永久吊死在 `read()` 里。`release()` 时读帧线程可能正卡在 `cap.read()` 内，`join` 也有 2s 上限。
- **摄像头重开不清计数，文件循环必须清零**（`_keeps_counts_on_restart(source)`）。摄像头停三秒（切到别的应用、驱动打了个嗝）之后人还在原地，若按文件那套把 `Tracker`/`OnlineCounter` 一起换掉，这一局已经数出来的几十次会被抹平；而且在线计数拿 `frame / fps` 当时间轴，帧号归零会让窗口里刚攒起的节律一起作废。文件读到结尾是"同一素材重播"，帧号与计数都必须归零才和画面对得上。回归用例 `TestCameraRestartKeepsCounts` 用"每次只给 5 帧然后就停"的假摄像头把两种语义都钉住。
- **推理报错不再静默弄死整场**。`_loop` 原先只在最初打开画面源那一句外面有 `try`，跑一半 `detector.detect()` 抛异常（显存不够、素材被写坏、`device` 写错）时线程直接死掉，而 `running` 还停在 `True`、`error` 还是空——页面上是"实时计数中 + 数字悄悄不再涨"，一节课数下来没人发现自己白跳了。现在分三层：偶发一帧失败就跳过并写 `error`（页面上看得见，下一帧成功自动清掉）；连续 `MAX_DETECT_FAILURES=30` 帧都失败才升级成异常；`_loop` 外层 `try/except/finally` 接住任何异常，写下 `实时链路异常停止: <原始报错>` 并把 `running` 置假，计数原样留在 `state` 里供页面显示停在哪个数。
- **`device` 必须在控制接口就挡住**。这个值会被原样交给 `model.predict(device=...)`，写错时的表现是**每一帧推理都抛异常**，和画面源坏了长得一模一样。`_checked_config_value` 现在只收 `cpu / mps / cuda / cuda:N / 0 / 0,1`（大小写归一后校验），其余直接 400 报错。
- **切画面源的写入必须和主循环用同一把锁**。主循环是"读出 `pending_source` 再置空"两步，连着点两次切源时后一次会被前一次的置空抹掉：页面显示选了 B、实际还在播 A。现在两边都在 `engine.lock` 里。
- **不要顺手设 `CAP_PROP_BUFFERSIZE=1`**。这是驱动侧压延迟的常见写法，实测在这个素材上会把解码拖到约 1.6 帧/秒（相差 20 倍），取帧线程本身已经把延迟压到一帧，这个属性只剩风险。

这一层对计数精度是中性的：6 段素材整段复算走的全是文件路径，第 9.2 节的基线一格没变（改动前后各跑一次逐字比对）。

### 6.16 灵敏度滑杆（`config.sensitivity_to_gains`）

页面 1~100 一根滑杆，同时驱动三道门限（只松噪声一项的话滑到一半就没反应了）：

| 端点 | `snr_k` | `peak_frac` | `floor_relief` |
| --- | --- | --- | --- |
| 1（最严） | 5.4 | 0.15 | 1.6 |
| 50（默认） | 3.0 | 0.08 | 1.0 |
| 100（最松） | 0.4 | 0.025 | 0.4 |

插值为分段**指数** ramp（`_ramp`），保证每滑一格的感知变化大致相同。`snr_k_to_sensitivity` 是反函数，用于把实际生效阈值显示回页面刻度。

两个已定的边界决定：

- 上端不敢放到接近零：实测滑杆推到 95 时总计数比实际多两三成（一次起跳被数成两个）。
- 上端一度收得太紧也是错的：170px 身高的人真实起跳在踝部只留 1~2px，早期最松一档只能把下限松到 1.4px，半数真起跳仍在阈值下（整段只数到实际一半），所以整体再往下放一档，让滑杆上半段有可感知变化。

有测试锁住这些性质：端点值、单调性、越界钳制、反函数往返、三道门限同步松动、默认值与 `Config` 一致。

## 8. 指标口径与验收

### 8.1 有真值时（人工逐次标注）

`jumpcount/evaluate.py`：按水平位置把预测轨迹对上标注的人（位置缺失时退化为按计数排序对齐），支持事件级匹配。

- 事件匹配容差：`max(tolerance_sec, tolerance_ratio × period)` = `max(0.15s, 0.4 × 周期)`。
- 指标：每人的 `precision` / `recall` / `f1` / 计数误差 / MAE，事件级 `matched` / `false_positive` / `missed`。
- 标注格式：`gt-template` 生成 JSON 模板，`name` / `center_x` / `count`，可选逐次 `events`（秒）；也支持 CSV（`name,count[,center_x][,events 分号分隔]`）。

### 8.2 无真值时的三个代理指标（`out/tune/quick.py`）

| 指标 | 定义 | 方向 |
| --- | --- | --- |
| 双计特征 | 相邻起跳间隔 `< 0.7 × 周期` 的占比 | 越低越好 |
| 回捞峰自身双计率 | 回捞峰的左右邻间隔 `< 0.7 × 周期` 的占比 | 越低越好 |
| 节奏离散度 CV | 峰间隔的 `std / mean`，逐轨迹算再取均值 | 越低越好 |
| 虚高条数 | `计入 > 1.05 × expected_count` 的轨迹条数 | 越低越好 |
| `rhythm_coverage` | `total_count / (rate_hz × duration)` | **自我一致口径，见下** |

**`rhythm_coverage` 的陷阱**：它用"自己的节奏"当分母，数得越多分子分母一起涨，**永远报不出"数过头"**（实测虚高恒为 0）。所以发现"补太多"只能靠双计特征与节奏离散度。绝对准确率必须人工逐次真值才能定标——这是当前唯一的精度空白。

**反过来的陷阱同样存在：`expected_count = rate_hz × duration` 也不可信，"完整率"不能当漏算量尺。**
节奏估偏短时分母虚高（`179023471330 #9`：`rate_hz = 4.167`，整段却只数到 30 次——这个频率真跳的话应该是 100+ 次），
估偏长时分母虚低。完整率只用于**同一批素材、同一判据下的趋势对照**，
判断"某个人到底数没数对"必须用 `out/tune/render_track.py --plot / --st` 目视，或用 `out/tune/probe_corate.py` 看他道作证率。

**他道作证率**（`out/tune/probe_corate.py`，本轮新增，用于回答"多出来的峰是不是关键点抖动"）：
每一次起跳，另外两条身体通道在同一时刻 ±0.25 周期内有没有一个达到自己阈值 0.5 倍的鼓包。
真起跳全身一起离地，任何一条通道都该跟着动；某个通道的抖动只出现在它自己那一维。
当前快跳组（≥2.4Hz）87.9%、慢跳组 72.2%，作为后续改动的对照组基线。

**作证率按事件类别拆开看**（`out/tune/probe_phaseproof.py`，日志 `out/tune/R_phaseproof.log`）——
同样是"多出来的峰"，来路不同可信度差很多，混在一起看会误判某条召回改动"质量一样"：

| 事件来路 | 他道作证率 | 解读 |
| --- | --- | --- |
| 实测起跳（`kind="jump"`） | 65.4% | 天花板：连真起跳都只有六成半能被别的通道在 ±0.25 周期内证实（关键点漏检 + 采样率限制） |
| 包络回捞峰 | 43.1% | 接近实测的一半以上，可接受 |
| 按节奏补齐（常规） | 39.0% | 与"信节奏"这一类改动的合理区间 |
| 节拍格认领（`grid_fill_frac`） | 38.7%（边际） | 与常规补齐同级 → 支撑默认值 0.3，不支撑更低的 0.2 |
| 遮挡相位旁路 | 23.1% | **天然无法作证**：整段被挡住时别的通道同样看不见，所以这一类只能靠相位判据与真值定标，见第 12 节 |

**"应有次数"从这一轮起有两个口径并存**（`quick.py` 同时打印，`summary` 里叫 `expected_by_rhythm` / `expected_by_rhythm_visible`）：

| 口径 | 定义 | 用途 |
| --- | --- | --- |
| 墙钟口径 `expected_count` | `rate_hz × duration_sec`（整段时长） | **只用于虚高判定**（`total > 1.05 × 应有`）与趋势对照 |
| 可见段口径 `expected_visible` | `rate_hz × observed_sec`（人真在画面里的秒数） | 衡量"数得全不全"。缺口归因显示整段口径有 46% 的"应有"落在人根本不在画面的时段上 |

起点 4951 → 终点 5656，墙钟口径完整率 0.698 → 0.797，而**可见段口径是 0.836 → 0.955**。
两条都必须留着：只报可见段口径会掩盖"遮挡时段的漏算"，只报墙钟口径则永远追不平；
把 `expected_count` 整体换成可见段口径实测会让虚高判定从 2 条涨到 33 条
（频率低估 10% 就误判三成轨迹，见第 10 节）。

## 10. 调参结论与禁区（已扫描过，勿重复投入）

| 结论 | 证据 |
| --- | --- |
| `recover_gap_ratio` **不要往回收到 0.6** | 0.6 → 回捞自身双计 6.93%；0.75 → 0.32%，代价约 5 个计数 |
| `recover_center_tol` 取 0.35 | 扫描：0.0→3673、0.25→3820、0.35→3845、0.45→3855、1.0（等于关闸）→3871。**绝对双计对数恒为 203**，说明这道闸在真实素材上不减少双计，只压"静止者抖动被排成节拍"的幻影（合成用例 16→12，且这类轨迹本就被参与判定挡在总数外） |
| 两道节拍闸分工不同 | gap 闸治双计，center 闸治幻影。用同一个指标看会误判其中一道"没用" |
| `envelope_lead_votes=1` 可再多约 20 个计数、双计不涨 | 默认保留 2，作为"多通道同时刻佐证"的保险；追求极限召回可放开 |
| 通道择优**在"打分口径"上已饱和**，但在"排序键"上没饱和 | 三条通道的分数几乎相同（踝 0.794 / 髋 0.792 / 头 0.779），做更细的打分是白投入；本轮改的是**排序键**：同清晰度档内比"谁数得出的起跳多"，+97 次且双计不涨（`channel_prefer_rate_margin=0.15`，见 6.6 与 9.4） |
| 阈值上限地板 `threshold_cap_floor_frac` 暂**不启用**（开关保留） | 取 1.0：4700 → 4666，双计 2.48% → 2.19%、回捞双计 0.61% → 0.20% 都变好，但实时从 4750 掉到 4532，逐条差分是"快跳者变好（`179023428267 #18` 11→69）、远景慢跳者变差（`179023484385 #22` 27→2）"的两头换，净效果与"先把快跳数全"相反。日志 `DOC_capfloor.log`，台账 `tracks_cf_base.tsv` / `tracks_cf100.tsv` |
| 头部零位移闸门**不要再收紧** | `min_head_move_px 1.0 → 2.0` 实测**一次都不生效**（近门槛的 8 条全卡在占比条件 `head < 0.30 × body` 上，位移条件从不成立）；`min_head_share 0.30 → 0.35` 只 −6 次。要动这道闸，先动占比而不是位移 |
| `smooth_fast_min_rate` 停在 2.0，**不要放到 1.5** | 1.5 档 +122 次、双计持平，但他道作证率显示被换轨迹从 ≥64% 掉到 27.9%（`179006213119 #11`），即多出来的峰没有旁证；2.0 档 +23 次且双计降到 2.40%、作证率 88.9%→87.9%（`DOC_smfast_trigger.log`、`DOC_corate.log`） |
| `smooth_fast_gain 1.15 → 1.05`、`min_extra 8 → 4`、`margin 0.05 → 0.10` 都不划算 | 分别 +21（回捞反降 72）、+1、−17（双计升到 2.55%）。窄窗的换档条件已到位 |
| 补齐证据闸门 `fill_min_lift_frac` 取 0.35 | 0.2 → +59（证据太薄，等于回到无闸门），0.6 → −93（把真快跳的补齐也拦了） |
| `max_fill_per_gap` 停在 3，**不要放到 4** | 4 档 +45 次且双计不变，但一次空档要用"内部有一处鼓包"这一条证据撑四次计数，与"没跳不计数"冲突（`DOC_chrate20.log`） |
| `rhythm_measure` 保持 `band` | 换成 `period` −143 次，`period` + `keep_rhythm_strength=0.20` −113 次：召回换精度，方向相反 |
| `smooth_win=1` 全局换窄窗否决 | +223 次但双计 3.08%、CV 0.735，噪声与真拍一起进来；只作为快跳第二档按需启用（6.10.1） |

| 缺口里有 42.7% 是算法无解的 | 总缺口 1673 中"未观测"占 714（遮挡/半速播放），人不在画面里就没信号（`out/tune/probe_deficit.py`，`deficit.json`） |
| 静止者合成用例会造 5~12 个幻影 | σ=0.3 抖动时回捞会造幻影，但 `verdict=out` 被参与判定挡在总数外，不影响总量 |
| 灵敏度滑杆上端既不能到零、也不能收太紧 | 95 时多两三成（双计）；早期上端太紧则整段只数到一半 |
| `max_rate_hz` 与三处 `hard_min`、一处 `lo` 是**同一个旋钮**，取整口径必须一致且一律向下，勿只改一边 | 见 6.10.1。只改离线会让实时先锁相、只改实时会让两边对不上；`round` 会让取峰器比验收闸门更严，频率带顶端出现取不到的空洞。`tests/test_core.py::TestFastJumpNoPhaseLock` 会拦住 |
| `max_rate_hz` 继续往上调（5.0 及以上）换不来东西 | 25fps + `smooth_win=3` 下 5.0Hz 的合成达成率已经掉到 0.39（`period_source` 落到 `fallback`），回捞峰自身双计同时从 0 涨到 0.41%。要覆盖 >4.5Hz 得换帧率，不是换这个参数 |
| 空档取证的票数**不要提到 3** | 扫档（离线，配 `fill_cap_expected`）：0 票 → 4951、**1 票 → 5170**、2 票 → 5110、3 票 → 4981。3 票比 0 票还少，等于花钱买了个更差的闸门（`out/tune/R_votes_cap.log`） |
| 取证通道集合**不含 `box_center`** | 它与 `box_bottom` 同源（同一个框的两条边），一起投票等于同一个观测算两票，2 票闸门形同虚设。集合固定为 `counter.LIFT_EVIDENCE_CHANNELS` |
| 遮挡相位旁路**必须**限定 `coverage < min_fill_coverage` | 人站着没跳的那段位移是平的但一直被观测，两端峰距常常正好是整数个周期（相位残差≈0），不加限定就把"没跳"判成"节奏没断"凭空补数。`tests/test_core.py::TestUndercountRecovery::test_absent_person_is_not_backfilled` 抓到过，修法是给用例造一段真脱拍（`_samples(delay=7)`），不是放宽闸门 |
| 相位容差**不要放到 1.0** | 1.0 等于放弃相位判据：再多 254 次但虚高从 2 条涨到 3 条；0.35 只比 0.25 多 107 次而噪声踩格概率翻倍（`out/tune/R_phase_tol.log`） |
| 节拍格认领**不要降到 0.2** | 0.2 档的认领幅度 0.16px 已低于该素材噪声 0.24px，新增认领峰的他道作证率只有 38.7%（实测起跳 65.4%、包络回捞 43.1%），多出来的 29 次没有信号支撑（`R_grid_sweep.log`、`R_phaseproof.log`） |
| 实时补数上限的尺子**不要只用全局 `period`** | 全局周期被 2:1 锁成两倍时预算只剩真实拍数的一半，快跳的人被上限整个卡死不补：实时 5086 → 5054。必须 `min(period, scale)`，与离线同源 |
| `expected_count`**不要整体换成可见段口径** | 换成 `expected_visible` 后虚高判定从 2 条涨到 33 条 —— 频率低估 10% 就会误判三成轨迹。两条口径必须并存，各管各的事（见 8.2） |
| `stats["recovered"]` **必须与事件标记同数** | 它现在在 warmup 过滤之后与 `recovered` 标记一起统计；改回在过滤前累加，`tests/test_recovery.py::TestRecoverGates::test_count_track_never_counts_less_with_envelope` 会报"stats 与事件标记不一致" |
| `amplitude_ratio` 抬到 0.012 已否决 | 与"明显离地"判据 `min_lift_ratio=0.012` 对齐看着合理，实测总量 4844→4443、在跳绳 73→65，但按抬脚比分组差分后有 **206 次损失落在抬脚比 ≥3% 的人身上**（例如 `179023428267 #23` 抬脚比 13.5%，41→22），误伤真跳绳者。差分脚本 `out/tune/diff_tracks.py`，台账 `tracks_final.tsv` / `tracks_amp12.tsv` |
| `snr` **不能**当误剔/误计的判据 | 方向是反的：站着不动的人噪声近零 → 信噪比虚高（8~99）；真跳绳者快速运动抬高 `hf_sigma` → 信噪比反而只有 1.7~2.8 |
| `height_cv` 这道闸不要放宽 | "被剔除但仍数到 128 次"里有 95 次来自两条**坐在台阶上的观众**轨迹（靠 `height_cv=0.26` 才挡住），肉眼审核 `out/tune/audit_tracks.py` 已确认 |
| 幅度类护栏治不了双计 | 双计 152 对全部是两个实测峰，较弱那只的幅度中位数 0.98× 正常峰——按幅度切（阈值 0.5×）只能涉及 3 个，白搭 |
| 剩下的漏计有一半是算法无解的 | 总漏计 1768 中"该帧根本没有观测"占 48.9%（遮挡/人出画），另有 21.0% 空档里连鼓包都没有；次阈值从 0.7× 再往下压只能碰到 8.7%，而鼓包落在节奏格（偏差 <0.25 周期）的只有 1.6%，盲压风险大于收益（`out/tune/probe_missed.py`） |
| 没有系统性的"一个人被拆成两个人" | 嵌套框包含率 >0.6 的组合数为 0（`probe_nested.py`）；同帧两人纵向位移相关性 r≥0.8 的组合数为 0、p99 仅 0.5（`probe_paircorr.py`） |

## 11. 已调研并否决的外部方案

| 方案 | 否决理由 |
| --- | --- |
| MediaPipe / YOLO + 阈值规则的同类跳绳仓库 | 判据比本仓库更粗（多为单通道阈值 + 峰计数），没有解决"远景 1~2px 起跳"和"双计" |
| 监督式动作计数（PoseRAC、Countix 等回归/排序式） | 需要重训或标注训练集，违反"用现有权重模型"的前提 |
| ByteTrack / BoT-SORT 换掉手写跟踪 | 会引入第二套身份体系，与站位（`slot`）身份冲突；本仓库的第一号误差是 ID 漂移，但解法是站位 + 归并，不是更强的关联器 |
| scipy `filtfilt` + Butterworth | 会新增 scipy 依赖；FFT 零相位实现等效且更短 |
| 把中值窗口拉长以压噪声 | 先消失的总是小幅起跳，与目标相反；改为带通 |
| 双踝取均值 | 交替抬腿的跳法会把一半起跳压到阈值下（实测 29 vs 45） |
| 整段分位数算水平活动范围 | 一次 ID 漂移就放大成"走了几倍身高"，误剔真人；改为逐窗中位数 |
| 直接把缺失通道换成框底边 | 留下台阶，台阶本身被当成一次起跳；改为中位差平移补齐 |
| 群体节拍共识（用整组人的公共节拍定格子） | 250 个候选轨迹对里公共节拍的 Pearson R ≥0.8 的**一对都没有**（`out/tune/probe_pace.py`）：多人跳绳时每个人各跳各的节奏，"跟着摇绳人"这个前提在素材里不成立。所以节拍格只能由**这条轨迹自己的已认峰公共相位**定出（见 6.12.1），不引入跨人信息 |

## 13. 复现时容易踩的坑

- **不要动 `Config` 之外的阈值常量**：阈值全部集中在 `Config`，`from_json` 会拒绝未知键（拼错参数名会报错而不是静默失效）。滑杆常量在 `config.py` 模块级，不在 `Config` 里。
- **`gap_candidates` 必须返回 `(位置, 档位)` 并且在复核时沿用同一档**。改成只返回位置 = 弱起跳刚被捞出来又被票掉。
- **`refine_peak` 之后必须二次去重**，否则最终 `nms_by_height` 会把实测峰顶掉（总数看着没变，实际把真峰换成了回捞峰，`recovered` 统计失真）。
- **在线与离线的噪声估计必须同一个口径**（都用 `hf_sigma_masked`）。不一致时实时/离线的对比全部作废。
- **新增参与判定字段时同步三处**：`counter.participation`、`online.TrackCounter.stats`、`web/app.js`。少一处会出现"离线剔了、实时没剔"。
- **`stats["signal_source"]` 里不要写字符串 `"none"`**：`TrackCounter.snapshot()` 用 `stats.get("signal_source") or (实际用过最多的通道)` 做退回，非空的 `"none"` 是"真值"，会把退回逻辑挡掉，页面上"信号"一栏永远是 none（实时跑 YOLO 时看着像通道择优没生效）。留空串才对。
- **节奏类资格必须有过期机制**：`period_frames`、`rhythm_strength` 只要有一个不清零，"停下不跳的人"就永远拿着"节奏清楚"的免死金牌继续加数。新增任何以节奏为前提的放行分支时，同时确认它在窗口空掉时会关掉。
- **离场寄存只接累计量**：把可见率、双脚同步性、信号窗口一起继承过来，就等于拿上一个老人的证据替新来的人签字，路过的人也能被提成"在跳绳"。
- **`fetch()` 在 HTTP 400 上不会 reject**：前端判成败要看返回体的 `error`，只挂 `.catch()` 会永远以为设置已生效。
- **状态条上的报错会被 500ms 轮询刷掉**：控制类报错要带时间戳短暂驻留（当前 4s），否则用户看不到自己哪一次点击失败了。
- **不要为了让测试通过而改判据**：`tests/test_recovery.py` 里"实测峰一个都不能丢"和"结果单调不减"是回捞的硬约束。
- **摄像头和文件的"读不到帧"是两件事**：文件读到结尾 = 同一素材重播，帧号与计数都要归零；摄像头停帧 = 设备抖动，人还在原地，归零等于把这一局数出来的次数抹掉。改动 EOF 分支时先确认自己走的是哪一个（`_keeps_counts_on_restart`）。
- **给摄像头设 `CAP_PROP_BUFFERSIZE=1` 之前先实测**：这是压驱动延迟的常见写法，本机实测把解码拖到约 1.6 帧/秒。取帧线程已经解决了积压，别再叠一层。
- **`device` 写错长得像画面源坏了**：它是原样交给 `model.predict()` 的，错值表现为每帧推理都抛异常。控制接口必须校验取值，异常路径必须把 `running` 置假并带上原始报错。
- **`fetch()` 在 HTTP 400 上不会 reject**：前端判成败要看返回体的 `error`，只挂 `.catch()` 会永远以为设置已生效。
- **写实时链路的用例别拿 `running` 当"线程已停下"的信号**：线程刚起来时它也是 `False`；每帧都失败的场合它从来没真过。判停要认 `error` 里那句终止原因本身。
- **`rm -f` 之类的删除在本机策略下会被拒**，需要删除时用不带 `-f` 的形式或换名。
- **后台跑调参脚本要用常驻会话**：普通 `(cmd &)` / `nohup ... &` 都会随本次工具调用一起被 SIGHUP 带走，日志留不下来。要么前台跑并轮询会话，要么在页面上另开终端。
- **`quick.py` 严禁并发**：它输出的三项 ms 是并发下最先被污染的数字（同一份缓存并发跑能从 3.3 ms 漂到 8 ms 以上），而归因用的 A/B 一旦 ms 变了就会被误读成"改动变慢了"。计数部分是确定的，ms 部分必须独占。
- **`apply_patch` 整批原子**：一批里任何一处 context 对不上，**整批一个字节都不写**，而报错只指出第一处。改一份长文档时逐处提交，或改用"逐条 assert 命中一次再替换"的脚本（本轮就是这么做的）。
- **离线加了判据必须同轮接进 `online.py`**：取证票数、相位旁路、节拍格认领、两条配额护栏，漏接任何一项都会得到"离线涨了、实时没涨"的假象，而第 8.3 节的回归会把这种半截状态固化成基线。
- **两套"应有"不能互相替换**：墙钟口径管虚高判定、可见段口径管召回评估（见 8.2）。只看前者会永远以为"还差 20%"，只看后者会把虚高漏掉。
- **zsh 不对未加引号的变量做分词**：`for f in $LIST` 只循环一次，`$LIST` 得写成 `${=LIST}` 或用数组。
- **`np.percentile` 要喂 `np.asarray(..., dtype=np.float64)`**：直接传 Python list 的 `int` 序列在部分 numpy 版本上会因插值方式不同给出不同的分位数，扫档就会出现"同一配置两次结果不同"。
- 上下文压缩约定（项目 AGENTS.md）：超过 168200 token 立即压缩一次，压缩时必须原样保留该规则本身。

### 把某一帧渲染成"人带框 + 次数"的图（A/B 肉眼核对的取样方法）

怀疑"多出来的人是不是真的在跳"时，不要只看统计量——把那一帧单独画出来看一眼。脚本要点（离线、不需要 GPU、不需要 YOLO，复用 `out/tune/cache` 的缓存）：

```python
import os, pickle, sys
sys.path.insert(0, "<repo>")            # 仓库根
sys.path.insert(0, "<repo>/out/tune")   # 为了 import harness
import cv2
from harness import CACHE, _detections  # 缓存读取与"缓存帧 -> Detection"的既有实现
from jumpcount.config import Config
from jumpcount.counter import count_track, participation
from jumpcount.identity import build_slot, consolidate
from jumpcount.tracking import Tracker

video, stop = "1790234843854.mp4", 700   # stop = 想看的帧号（1 起）
cfg = Config()
data = pickle.load(open(os.path.join(CACHE, video + ".pkl"), "rb"))
tracker, samples, centers = Tracker(cfg), {}, {}
for index in range(stop):                # 与 harness 完全同构地喂到第 stop 帧
    for tid, det in tracker.update(index, _detections(data, index, cfg)):
        samples.setdefault(tid, []).append((index, index / data["fps"], det.box, None, det.keypoints))
        centers.setdefault(tid, []).append(((det.box[0] + det.box[2]) / 2, (det.box[1] + det.box[3]) / 2))
slots = [build_slot(t, samples[t], centers[t]) for t in sorted(samples) if len(samples[t]) >= 2]
slots, _ = consolidate(slots, cfg)

cap = cv2.VideoCapture(os.path.join("<repo>", "跳绳素材", video))
cap.set(cv2.CAP_PROP_POS_FRAMES, stop - 1)   # 与上面 range(stop) 对齐: 最后处理的是第 stop-1 帧(0 起)
ok, img = cap.read()
cap.release()
for slot in slots:
    res = count_track(slot.track_id, slot.samples, cfg, data["fps"])
    verdict, _ = participation(res.stats, cfg)
    if verdict == "out":
        continue
    x1, y1, x2, y2 = slot.samples[-1][2]      # 该轨迹最后一次看到的框
    total = res.count + int(res.stats.get("filled", 0))
    color = (60, 200, 60) if verdict == "in" else (60, 200, 255)
    cv2.rectangle(img, (int(x1), int(y1)), (int(x2), int(y2)), color, 2)
    cv2.putText(img, f"#{slot.track_id} {total} {verdict[:3]}", (int(x1), int(y1) - 6),
                cv2.FONT_HERSHEY_SIMPLEX, 0.7, color, 2)
cv2.imwrite("/tmp/frame.png", img)
```

- **两个对照组要同帧、同 `stop`、同缓存**，只有被测开关不同；否则"多出来的人"可能只是取帧时刻不同。
- 帧号对齐最容易错：`range(stop)` 最后处理的是 0 起的第 `stop-1` 帧，取图时 `CAP_PROP_POS_FRAMES` 也必须写 `stop - 1`。
- 框取的是"该轨迹最后一次看到的框"，不是这一帧的框——被吃掉框的人在这一帧可能根本没框，这正是要看的现象。
- 优先挑 `harness` 归因表里"横向位置明确、有绳、被观测时长长"的新增计入者下手，核对成本最低。
- 生成的临时图不必入库，看完即删。
