# 多人跳绳计数与准确性分析

把一段多人跳绳视频拆成「每个人跳了多少个」，并且回答**这个数为什么可信 / 在哪一秒开始数错**。

## 流程

```
视频 → YOLO 姿态/检测 → 多目标跟踪(稳定 ID) → 每人垂直位移信号 → 自适应峰值计数 → 准确性审计 → 与人工计数对比
```

设计要点：

- **稳定 ID**：IoU + 预测中心距离混合关联，断轨保留重认领窗口，避免「同一个人被数两次」或「两个人并成一个」。
 - **站位身份**：固定机位下跳绳的人守在自己的圈里，位置比短时运动预测可靠。检测闪烁把跟踪 ID 切断时，按站位把碎片轨迹接回同一个计数器；否则一个人被拆成三条各数一段，每条可见率都被摊到 50% 以下，会被「可见率过低」整条踢出（实测漏计最严重的来源）。
- **位移信号**：优先脚踝关键点，其次髋/头，最后退化到检测框底边；先中值平滑再用滑动中值去基线，消掉相机抖动和身高/透视差异。脚踝这一帧被挡时换成髋/头补，并按两者同时可见时的中位差把读数平移回原通道——直接换源会留一个几十像素的台阶，台阶本身会被数成一次起跳。
- **参与判定三态**：`计入 / 低置信计入 / 剔除`。低幅起跳、遮挡偏多但节奏清楚的人不再整条归零，改成低置信计入并在页面和审计里标明；走动路人、双脚交替迈步、框高剧烈波动（ID 在不同人之间跳）仍然直接剔除。
- **自适应阈值**：用自相关估出每人自己的跳绳节奏，再按该节奏定最小峰间隔；幅值门限取「噪声 3σ / 框高比例 / 绝对像素」三者最大，且不超过信号自身幅值，人群里的小幅起跳不会被整段抹掉。
- **双摇与漏计**：间隔小于 0.62 倍周期判为一次起跳内的额外过绳（双摇），可按 `policy=jump`（按起跳数）或 `policy=rope`（按过绳数）出数；间隔大于 1.8 倍周期记为疑似漏计空档，默认按节奏补齐（`interpolate_gaps`）。
- **实测与补齐分账**：`count` 只算真正抓到的起跳，`filled` 单列按节奏补出来的个数，总量 = `count + filled`。混在一起会让灵敏度滑杆失去意义（门限再严也能靠补数追平），复盘也看不出哪些是实测。补的三道护栏：这段区间至少观测到 70% 的帧（人本来不在画面里就不替他猜）、节奏必须是实测出来的且够清楚、单个空档最多补 2 个。

## 安装

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
```

装完如果 `import cv2` / `import torch` 报 `library load disallowed by system policy`：是 `.venv` 里的 `.so`/`.dylib` 带着 `com.apple.quarantine` 被 macOS 的签名策略拦下（被拦的库还会被系统删掉，表现成 `No such file`）。清属性后重装这几个包即可，pip 的 shebang 若指向旧路径就用 `.venv/bin/python -m pip`：

```bash
.venv/bin/python -m pip install --no-cache-dir --force-reinstall --no-deps numpy opencv-python torch
```

## 实时页面

对着摄像头开一个网页，画面里每个人一张卡片，实时显示「跳了几个」和这个数可不可信。

```bash
# 对本机摄像头
.venv/bin/python -m jumpcount.server \
  --source 0 --weights 跳绳素材/yolo26s-pose.pt --device mps

# 对视频文件（没有摄像头、或想先复现有素材时）
.venv/bin/python -m jumpcount.server \
  --source 跳绳素材/1790062131196.mp4 --weights 跳绳素材/yolo26s-pose.pt --device mps
```

然后浏览器打开 **http://127.0.0.1:8790**（页面顶部可切换摄像头与视频源，不用重启服务）。

「画面源」下拉每次刷新页面都会重新扫描 `跳绳素材/`（`--scan` 可指定别的目录，可重复），新丢进去的视频刷新一下就出现在列表里。

页面上能做什么：

| 控件 | 作用 |
| --- | --- |
| 画面源 | 摄像头与 `跳绳素材/` 下的视频互相切换；刷新页面重新扫描目录 |
| 计数口径 | 双摇按 1 个（按起跳）还是按 2 个（按过绳） |
| 灵敏度 1~100 | 起跳幅度门槛松紧；远景小跳、轻跳调高，误计多调低（默认 50，1 最严，100 最松）。整根滑杆同时松三道门限，上端已放到「噪声倍数 0.4 / 峰值比例 2.5% / 下限打 4 折」，人群远景素材上从 616 次推到 788 次（+28%） |
| 检测门槛 | 调低多检出人但易抖动，调高干净但易漏人 |
| 分析精度 | 远景小人必须用「高」，「省算力」只适合人离镜头近的场景 |
| 入围门槛 | 某人被清晰跟踪的时间占比低于此值就只观察不计数；遮挡严重的场面调「松」 |
| 暂停 / 重新计数 | 暂停保留当前数字；重新计数把所有人数字清零 |

颜色含义：绿色正在计数、黄色信号偏弱或**低置信计入**（低幅起跳、遮挡偏多，卡片上写明降级原因）、灰色走路路人不计入并附排除原因。右上角总数 = 实测 + 按节奏补齐，卡片上单独显示 `+N 按节奏补`。右侧「计数可信度提示」列出漏计空档、轨迹断裂、同一人被拆成两条等风险。

第一次用摄像头时注意：

- macOS 会弹「允许访问摄像头」，要选允许；若没弹，去「系统设置 → 隐私与安全性 → 摄像头」勾选运行命令的 App（Terminal / iTerm / Codex），再重跑命令。
- 用 `screen`/后台方式启动时摄像头可能起不来：日志会出现 `OpenCV: not authorized to capture video`、`can not spin main run loop from other thread`（后台进程没法弹授权框）。这种情况改在自己的终端里跑，或加 `OPENCV_AVFOUNDATION_SKIP_AUTH=1`；也可以先用视频源，页面顶部下拉随时切摄像头。
- Apple Silicon 一定加 `--device mps`：纯 CPU 只有 2~3 fps，画面会明显滞后。
- 觉得卡先看画面下面那一行：它按帧显示「每帧 Xms（推理 Yms · 画面 Zms）」。`画面` 现在只有 2ms，说明瓶颈就是模型推理，直接降「分析精度」最快。
- 实测各档（2560×1440 素材，同一台机器连续跑，取中位数）：

| 分析精度 | 单帧推理 | 约等于 | 平均每帧检出 |
| --- | --- | --- | --- |
| 1280 高 | 51.8ms | 19.3 fps | 6.55 人 |
| 1152 较高 | 48.1ms | 20.8 fps | 6.61 人 |
| 960 均衡 | 34.4ms | 29.1 fps | 6.08 人 |
| 640 省算力 | — | — | 远景小人明显漏检，只适合人离镜头近 |

- 试过但没用的两个方向，别重复踩：FP16（`quantize=16`）在这台 M 系列芯片的 MPS 上反而更慢（35ms vs 25ms），检出框逐像素一致；先把画面缩到 1280 宽再送进模型也更慢（59.2ms vs 51.8ms），因为模型内部本来就要缩，多缩一次只是白活。
- `--stream-fps`（默认 15）只限制往页面推图的频率，不省推理；出图比推理慢时浏览器会把帧攒在手里，画面上的数字就会比右上角慢好几秒。
- 端口被占用会直接提示换一个：`--port 8791`。
- 每个人站定 1~2 秒后才开始出数（需要先采一段信号估节奏），一开始显示 0 是正常的。

| 再叠加「修复断轨重认领的重复 ID」（见下文「断轨重认领的重复 ID」） | 3790 | 311 | 4101 | 4446 | 73 |

实时链路与离线复盘的差距从 27% 收到基本一致：以前实时会把「位置有漂移但双脚同步起跳」的真人整条剔掉（判定层拿不到双脚同步性），现在两边判据一致。

「被剔除但已数到的次数」从 114 涨到 502 不是退步：旧口径下一半轨迹在起步阶段就被整体否决，攒不到次数；现在碎片轨迹先累积再由「框高波动」这道闸拦下，代价从静默丢数变成看得见但确实不敢计入的次数。把遮挡宽限放宽到 25 帧之后这项降到 **289**，再修掉断轨重认领的重复 ID 之后降到 **128**——断裂少了、一个人的框不再被隔壁的人抢走，需要靠闸门兜底的碎片自然就少了。

已知边界（页面会逐条提示，不会静默出错）：

- 人站得极近或频繁换位时，跟踪会把两个人的框串起来，数字会在两人之间漂移；此时卡片上会出现「已接回 N 段轨迹」，数值仅供参考。
- 站着刷手机的大人偶尔会被当成轻跳者（起跳幅度约身高的 3%，和轻跳的孩子接近，单靠幅度分不开）。把「灵敏度」调低一档可以压掉。
- 被挡住的时段不一定补得回来：这段区间至少观测到 70% 的帧才按节奏补（`min_fill_coverage`），人整个不在画面里时不替他猜；页面提示「有 X% 的时间被遮挡或跟丢」，这部分是真漏计。

## 用法

```bash
# 1) 用 YOLO 姿态模型跑一段真实视频，逐人计数 + 自检
.venv/bin/python -m jumpcount run \
  --video 跳绳素材/1790062131196.mp4 \
  --weights 跳绳素材/yolo26s-pose.pt \
  --out out/v1

# 2) 生成人工计数模板，填完真实次数后对答案
.venv/bin/python -m jumpcount gt-template --out out/v1/gt.json --persons 4
.venv/bin/python -m jumpcount eval --pred out/v1/counts.json --gt out/v1/gt.json --out out/v1
```

产物在 `--out` 目录：

| 文件 | 内容 |
| --- | --- |
| `counts.json` | 每人次数（实测 `count` 与按节奏补的 `filled` 分列）、节奏、事件时刻、信号来源、信噪比、可见率、参与判定 `verdict`、审计结论；顶层 `total_jumps` = 实测 + 补齐，另给 `total_jumps_direct` / `total_jumps_filled` / `total_jumps_confident` / `expected_by_rhythm` / `rhythm_coverage` |
| `events.csv` | 每一次跳跃的时间戳与幅值，可对着视频逐条核 |
| `audit.json` | 自检问题清单（漏计空档、轨迹断裂、同一人被拆两条等） |
| `annotated.mp4` | 画了 ID 和实时计数的复核视频 |
| `accuracy.md` | 与人工计数对比后的准确率报告 |

常用开关：

```bash
--policy rope              # 双摇按过绳计 2 次（默认 jump 按起跳计 1 次）
--signal ankle|hip|head    # 强制指定跳跃信号来源
--conf 0.5                 # 提高检测门槛
--max-rate 3.0             # 收紧合理节奏上限
--interpolate-gaps         # 按节奏补齐疑似漏计空档(现已默认开, 关掉用 --set interpolate_gaps=false)
--set max_age=25 reid_window=80   # 直接覆盖任意配置项
--max-frames 500           # 先跑前 500 帧快速验证
```

## 已内置的准确性诊断

| 诊断码 | 含义 |
| --- | --- |
| `SPLIT_TRACK` | 两条轨迹长期同位置重叠，同一个人被数了两次 |
| `MERGED_TRACK` | 长期共存但相距很远，怀疑有人被并掉漏计 |
| `ESTIMATED_MISSES` | 出现超过 1.8 倍周期的空档，中间大概率漏计 |
| `TRACK_FRAGMENTED` | 轨迹频繁断开，断档期跳跃会丢 |
| `LOW_SNR` / `WEAK_RHYTHM` | 起跳幅度压不过噪声，阈值只能靠默认值兜底 |
| `SMALL_TARGET` / `LOW_VISIBILITY` / `LOW_CONF` | 目标太小、遮挡太重或检测质量差 |
| `CROWD_OVERLAP` | 画面中框重叠严重，跟踪 ID 极易互串 |
| `PROVISIONAL` | 该轨迹证据偏弱（低幅起跳 / 遮挡多），已按低置信计入总量并写明原因 |
| `FILLED_GAPS` | 有 N 个空档按实测节奏补齐，单列出来便于对着 `events.csv` 核对 |
| `SIGNAL_SUBSTITUTED` | 三成以上帧的关键点靠其它身体部位平移补齐，信号质量打折 |
| `AMPLITUDE_CLAMPED` | 振幅阈值贴着信号幅值，小幅起跳可能被整段切掉 |

## 少数（漏计）的成因与现在的处理

| 成因 | 旧行为 | 现在 |
| --- | --- | --- |
| 低幅起跳（离地不足身高 1.2%） | 整条轨迹剔除，人还在跳但次数归零 | 节奏清楚就低置信计入，`lift_ratio` 与降级原因都写进审计 |
| 遮挡/跟丢造成峰缺失 | 只记 `estimated_misses`，不进总数 | 按实测节奏补齐（默认开），补的个数单列 `filled` |
| 绝对像素下限 2px 当家 | 近机位低幅起跳被整段切掉（实测只剩 7/15） | 阈值下压时只压到「框高比例下限」，像素下限不再封顶 |
| 绝对像素下限不随远近缩放 | 远景的人只有 140~170px 高，一强一弱交替抬腿时弱的那一半（1~1.4px）全被 2px 下限埋掉，已计峰间隔正好是节奏的两倍（实测 `1790234282676` 里数到 75、实际约 106） | 下限按框高等比缩小（`amplitude_ref_height`，`amplitude_floor_min` 封底）；合成用例里同一信号 23 → 44 |
| 灵敏度滑杆上端收得太紧 | 最松一档仍有「噪声倍数 0.8 / 峰值比例 5% / 下限只打 7 折」，远景低抬腿整段够不着，用户推到 100 也看不到计数变化 | 上端放到 0.4 / 2.5% / 4 折；同一段人群素材整段复算 616 → 788（实时） |
| 遮挡 0.6s 就断轨 | 16 人群像里人挡人一秒是常态，断开这段的起跳全丢，还要重新热身 | `max_age` 15→25：离线 3353 → 3656、实时 3410 → 3779，被剔除但已数到的 470 → 289 |
| 实时每次出数都重算三条通道得分 | 计数环节耗时从 5.0 涨到 11.4 ms/帧，人群素材整体被拖慢 | 按 `channel_reselect_sec`（默认 1s）才重选一次，实测回到 5.6 ms/帧 |
| 双踝取均值 | 左右脚交替抬的跳法里，弱的那一半被均值抹平到阈值以下 | 默认取抬得高的一只（`ankle_combine=high`），6 段素材 3308 → 3353 |
| 噪声被插值段污染 | 缺口两侧大差分把噪声抬高 → 阈值虚高 → 更漏 | 噪声只用真正观测到的连续片段估计（`hf_sigma_masked`） |
| 阈值以下真起跳已经没有余量 | 位移阈值只能靠 `max_fill_per_gap` 盲补，护栏一挡整片丢；实时链路还在用被插值污染的噪声估计 | 换判据：在能量包络上找 + 空档 search-back + 多通道投票 + 节拍格四道闸（`recovered` 单列）；实时与离线统一走 `hf_sigma_masked`。6 段 3656 → 3845、实时 3779 → 3880，双计特征 6.03% → 5.75% |
| 关键点缺帧换源留台阶 | 直接切到框底边，台阶既造伪峰又埋真峰 | 按两通道中位差平移回原通道，`SIGNAL_SUBSTITUTED` 标明占比 |
| 判重只看水平距离 | 并排站的真人被并掉（实测一次并掉 268 帧观测） | 还要求重叠帧上的框真的叠在一起（`dup_iou_min`），同帧抑制同理（`dup_min_iou`） |
| 实时链路的判定拿不到双脚同步性 | 位置一漂移就只能整条剔除，同一个人在离线复盘是低置信计入、在页面上是 0 | 把 `ankle_sync` 一并交给判定层，实时与离线判据统一（实测找回 222 次） |
| 横向活动范围按整段分位数量 | 一帧 ID 跳到隔壁人身上，全程范围就变成「走了两三个身位」，原地跳的真人被判成走路 | 逐 3s 窗口量再取中位数（`drift_window_sec`）：真走路每个窗口都在动，抖动只影响个别窗口 |
| 信号源写死优先脚踝 | 人远或低抬腿时脚踝位移只有 1~2px，一半真起跳压在阈值下（实测 `3c5e84…` 的 #6 只数到 47，实际约 55；这段里 7 条轨迹全部如此） | `auto` 改为在踝/髋/头里挑节律最清楚的（`channel_select=rhythm`），换通道要净胜 `channel_switch_margin`，三条通道的得分写进 `channel_scores` |
| 热身期与碎片各付一次代价 | 断裂越多丢得越多 | 补漏护栏保证不因断裂虚增，`fragments` 继续提示风险 |

判断改得好不好，看两个内部指标：`rhythm_coverage`（按每人实测节奏应有次数的达成率）与「被剔除但已数到的次数」。前者越接近 1 说明漏得越少，后者越小说明少有人被整条误杀。

### 个例复盘：`3c5e84…` 的 6 号为什么只数到 47（实际约 55）

- 他离镜头远（框高 149px）且小腿几乎不抬：脚踝垂直位移 p95 只有 2.7px，噪声 0.37px，计数阈值 1.21px —— **一半真起跳的峰值就压在阈值线下面**（16 个候选鼓包里 13 个只有 0.5~1.2px）。
- 实测直接峰只 29 个；节奏层认出 26 个缺口，`29 + 26 = 55` 与人工计数吻合，但每个空档最多补 2 个（`max_fill_per_gap`），只补回 18 个 → 47。
- 当时把灵敏度拉高救不动：阈值被「不超过信号 45%」这条夹在 1.21px，`floor_relief` 压到 0.3 也只多找回 2 个直接峰。（这是改前的结论；绝对下限已改成按框高缩放、滑杆上端也放开了，见下一节。）
- 换身体部位才是对症的：用髋取信号，直接峰从 29 涨到 45，节律强度 0.49 → 0.72，总数 54。这 21 秒里 7 条轨迹全部是踝最差、髋或头最好。
- 现在挑完通道后 6 号数到 54；同一段素材总次数 249 → 321，判为在跳绳的人从 9 个到 12 个。

### 个例复盘：`1790234282676`（16 人群像）整段少两三成

- 用户报这段的 6 号实际约 106 个（约 3.0Hz），页面只数到 75。对这条轨迹做「鼓包普查」：把阈值压到当前的 1/10，信号里也只能数出 38 个鼓包（2.5Hz）——**阈值这边已经没有东西可捞**。
- 剩下的缺口在观测连续性：这条轨迹只有 47% 的帧真正观测到这个人（16 人互相遮挡 + 检测闪烁把 ID 打断），而断掉的区间被「空档至少观测到 70% 的帧才补」（`min_fill_coverage`）挡着，不替他猜。
- 另一半是算力：这段 1920×1080、25fps、16 人同跳，这台机器只能跑到 11~13 fps（推理 56ms/帧 + 跟踪计数 17ms/帧），页面本身是半速播放，计数自然跟着慢一半。
- 对症的改动是少断几段：`max_age` 15→25（遮挡宽限 1 秒）。这段离线 526 → 747、实时 622 → 702；6 段合计「被剔除但已数到的」470 → 289。
- 配合「像素下限按框高缩放」和滑杆上端放开，滑杆重新有了反应（这段实时）：最严 648 / 默认 702 / 最松 841，改前整根滑杆推到底也只多几个。远景人群建议推到 75~100。
- 再往上就得加算力或降画质：25fps 跑不满时，观测率上不去，阈值再松也补不出没看见的起跳。

### 能量包络回捞：从心电 R 峰检测借来的那一套

阈值这条路的余量已经用尽（远景真起跳在踝部只剩 1~2px，再松先进的是噪声），于是改判"能量"而不是判"位移峰"。
心电里的 R 峰检测（Pan-Tompkins / Hamilton，可参考 NeuroKit2）面对的正是同一个问题：真信号幅度跨度大、噪声与信号同带、漏一个就是一个计数、多算一个就是虚假计数。
同类跳绳计数仓库（MediaPipe/YOLO + 阈值规则）没有更聪明的判据，监督式动作计数（PoseRAC、Countix）要重训权重，都不符合"用现有权重"的前提。

流水线在 `jumpcount/signal.py`（`bandpass` / `energy_envelope` / `gap_candidates`）与 `jumpcount/counter.py:recover_peaks`：

1. 零相位带通 0.7~4.0Hz（FFT 实现，不引 scipy、不产生相位漂移——相位一漂整段计数就整体错位）；
2. 差分 → 平方 → 滑动积分（窗 = `envelope_win_ratio` × 节奏周期）得能量包络：一次起跳的上升沿与落地沿并成一个鼓包，双摇不会各算一个；
3. 在包络上按同一套不应期取候选；再对"按节奏本该有起跳却没数到"的空档与首尾段逐档压低阈值 search-back（`search_back_ratio`、`search_back_levels`），候选带着自己那一档一起出来；
4. 候选落回原始位移取高点（`refine_peak`），四道闸依次签字：
   - 这段区间至少观测到 `recover_min_coverage` 的帧——人不在画面里不替他猜；
   - 原始位移 ≥ `recover_raw_ratio` × 正常阈值——包络说是起跳不算数，位移上得真有个鼓包；
   - 至少 `envelope_lead_votes` 条身体部位通道在同一时刻各有自己的包络鼓包——真起跳踝/髋/头一起动，单通道抖动不会；投票阈值沿用候选那一档，否则弱拍刚被捞出来又被票回原阈值；
   - 落点必须踩在节拍格上——与左右邻居都拉开 `recover_gap_ratio` × 周期（0.75），且落在左右实测峰的正中 ±`recover_center_tol`（0.35）；站着抖的人也凑得出"空档"，这条专治幻影。

这两道"节拍闸"的分工不同，实测数据说得很清楚：`recover_gap_ratio` 从 0.6 收到 0.75，把回捞峰自己的双计率从 6.9% 压到 0.3%（一次起跳数两遍基本绝迹）；`recover_center_tol` 在 6 段素材上一个双计对都没少（都是 203 对），它换的是"静止者抖动被排成节拍"那类幻影——合成用例里静止者的误捞从 16 降到 12（且这类轨迹本来就被参与判定挡在总数之外）。收到 0.25 要多丢 51 个计数而双计不变，放到 1.0 等于关掉这道闸。
5. 事件带 `recovered` 标记，页面卡片与事件流单独显示「+N 包络回捞」，与实测峰、按节奏补的数分列。

### 断轨重认领的重复 ID：一个人的框被隔壁的人抢走

`Tracker._revive()` 把断开的轨迹认领回来时只把它加进 `active`，漏了从断轨池 `finished` 里摘掉。于是这条轨迹**第二次**断开时会被再塞一次进池子——同一个对象在池里留下两个引用。之后只要有一帧里同时出现两个都能匹配上的框（人挨着站，或检测器给出重复框），`used_f` 是按**下标**去重而不是按对象去重，两条引用能把同一条轨迹认领两遍：`active` 里出现两个自己，`tracker.update()` 同一帧返回两个相同轨迹号，框位与命中数一帧写两次。

后果不止重号。认领的判据是中心距离（`reid_dist` × 框高）而不是 IoU，第二条引用会顺手把**隔壁那个人**这一帧的框也吃掉：那人当场没有轨迹，要等下一帧才重新起号。人挨着站的群像里，被吃掉的人整段容易被并进旁边的人身上，表现就是"少几个人、剩下几个人的数字在两人之间来回漂"。

修法只有两行：认领成功后按下标倒序把这条轨迹从 `finished` 里 pop 掉（与同一函数里吃掉 `pending` 的写法一致）。回归用例是 `tests/test_core.py` 里的 `TestTrackingGuards.test_a_revived_track_leaves_the_broken_pool` 和 `test_duplicate_boxes_cannot_revive_the_same_track_twice`——把 pop 那两行注释掉，第二条立刻报 `同一个人被认领了两遍: [1, 1]`。

### 摄像头画面越走越晚：把取帧拆成独立线程

单线程的 `read → 推理 → 跟踪计数 → 出图` 对视频文件没问题（帧由我们自己拉，多慢都不影响计数），但摄像头的出帧节奏由设备定：这一环比 30fps 慢，帧就在驱动队列里越积越多，页面画面越走越晚、延迟单调累积，屏幕上数的是几十秒前的人，而且没有任何地方能看出落后了多少。

现在摄像头源走 `engine.FrameFeeder`：一个线程只管从驱动读帧并**覆盖**同一格，主循环每次拿到的都是当下最新一帧，没被取走的旧帧直接丢（`dropped()` 就是这个数，它持续上涨说明推理跟不上帧率）。暂停时线程继续覆盖同一格，恢复后拿到的是当下这一帧——原来暂停三十秒再恢复，页面要先花三十秒补播攒下的旧帧。**视频文件不走这条路**：计数用的是原始帧，覆盖式取帧等于把中间的帧丢掉。

顺带把"读不到帧"分成了三种语义，以前它们共用一套处理：

| 情况 | 以前的行为 | 现在的行为 |
| --- | --- | --- |
| 摄像头短暂停帧（切应用、驱动打嗝） | 重开时把跟踪与计数一起换掉，这一局数出来的次数被抹平 | 只换捕获器，跟踪/计数/帧号继续，超过 `CAMERA_READ_TIMEOUT=3s` 才算停 |
| 文件读到结尾 | 归零重播（本来就对） | 不变 |
| 跑一半 `detector.detect()` 抛异常 | 线程静默死掉，页面还显示"实时计数中"，数字悄悄不再涨 | 偶发一帧只跳过并把原因写到"提示"；连续 30 帧失败才停下，状态改成"实时链路异常停止: <原始报错>"，计数留在页面上 |

`--device` / 页面的设备参数现在也会先校验（只收 `cpu / mps / cuda / cuda:N / 0 / 0,1`）：这个值原样交给 `model.predict()`，写错时的表现是每帧推理都抛异常，和画面源坏了长得一模一样。顺带说一句踩过的坑：**别给摄像头设 `CAP_PROP_BUFFERSIZE=1`**，本机实测把解码拖到约 1.6 帧/秒，而取帧线程本身已经把延迟压到一帧。

这一层对计数精度是中性的：6 段素材整段复算走的全是文件路径，调参台的基线一格没变（改动前后各跑一次逐字比对）。
